# 영상 처리 상세 분석 결과 설계

## 목적

Jira `S15P21A501-316`은 영상 등록 입력 화면이 아니라 검수자의 영상 처리 상세 화면을 개편한다. 기존 10단계 처리 파이프라인은 유지하고, 그 아래의 대사 선택 내부 기록을 실제 AI 분석 산출물 확인 영역으로 교체한다.

## 사용자 과업

검수자는 한 화면에서 다음 질문에 답할 수 있어야 한다.

- 이번 처리에서 장면이 몇 개 생성됐는가?
- 각 장면의 대표 화면과 구간은 무엇인가?
- 장면 설명과 실제 채택 대사는 무엇인가?
- 어떤 태그가 최종 유효 태그로 달렸는가?
- 화면 속 글자가 추출됐는가?
- 결과가 없을 때 정상적인 빈 결과인지, 아직 처리 중이거나 실패한 것인지 알 수 있는가?

## 정보 구조

상단의 영상 기본 정보, 원본 영상, 최신 처리 상태와 10단계 파이프라인은 현재 구조를 유지한다. 파이프라인 아래에는 다음 순서로 결과를 둔다.

1. 선택한 파이프라인 단계의 결과 제목
2. 현재 장면 한 건의 대표 화면과 해당 단계 산출물
3. 파이프라인과 분리된 `최종 분석 결과`
4. 전체 장면·캡션·대사·태그 보유 장면 수 요약
5. 현재 장면 한 건의 대표 화면·캡션·최종 대사·태그·OCR

성공한 파이프라인 단계를 선택하면 운영 기록 대신 해당 단계가 만든 결과를 보여 준다. 장면 나누기에는 구간, 대표 화면 추출에는 프레임, OCR에는 화면 글자, 대사 관련 단계에는 출처와 최종 대사, 영상 설명에는 전체 캡션, 개체 추출에는 최종 유효 태그, 검색 단계에는 생성·반영 결과를 표시한다. 실패·진행 중 단계에는 결과를 만들지 않고 상태와 실패 사유·재시도 여부를 표시한다. 값이 없는 필드는 예시 문구로 채우지 않고 `생성된 ... 없음`으로 표시한다.

기존 `대사 처리 기록`의 첨부 자막 유무, 선택 단계, ASR 필요 여부, 후보 구간 수 등은 기본 결과 화면에서 제거한다. 성공 단계에서는 시도 횟수·시각 같은 운영 정보를 숨기고 실제 산출물을 우선한다.

단계별 결과와 최종 분석 결과는 서로 대체하지 않는다. 단계별 결과는 처리 과정을 확인하는 영역이고, 최종 분석 결과는 검색에 사용할 정보가 장면별로 어떻게 조합됐는지 확인하는 독립 영역이다.

## 상호작용

- 장면의 `영상에서 보기` 버튼은 상단 원본 영상을 해당 장면 시작 시각으로 이동시키고 재생을 시도한다.
- 대표 프레임은 기존 인증형 `GET /scenes/{sceneId}/thumbnail`을 재사용하고 화면 근처에서만 지연 조회한다.
- 단계별 결과와 최종 분석 결과는 각 영역에서 항상 장면 하나만 렌더링한다. 좌우 버튼과 방향키, 모바일 가로 스와이프로 장면을 넘긴다.
- API는 내부적으로 20개 단위 서버 페이지를 유지하되 페이지 경계도 같은 이전·다음 장면 동작으로 이어진다.
- 최신 run이 없으면 분석 API를 호출하지 않고 처리 결과가 아직 없음을 안내한다.
- 최신 run이 진행 중이면 현재까지 저장된 부분 결과를 표시하고, 상세 polling으로 run 정보가 갱신될 때 분석 결과도 다시 조회한다.
- 최신 run이 현재 검색 반영 run과 다르면 기존 상단 안내를 유지하고 분석 결과에도 `검색에는 아직 반영되지 않은 최신 처리 결과`라고 표시한다.

## API 계약

검수자 전용 조회를 추가한다.

```http
GET /api/v1/clips/{clipId}/runs/{pipelineRunId}/scenes?page=0&size=20
```

- `clipId`와 `pipelineRunId`는 양수다.
- run은 해당 clip에 속해야 하며 clip은 논리 삭제되지 않아야 한다.
- 정렬은 `scene.start_time_ms ASC, scene.scene_id ASC` 고정이다.
- `scene_index`는 이 정렬의 1-based 순번이다.
- `search_applied`는 요청한 run이 `clip.active_pipeline_run_id`인지 나타낸다.
- 대표 프레임은 최소 `keyframe_id`의 시각이다. 이미지 byte와 내부 저장 경로는 응답에 싣지 않는다.
- 태그는 미확정 후보나 반려된 값을 포함한 raw tagging이 아니라 `TagResolutionPolicy`를 통과한 최종 유효 태그다. active run이 아닌 최신 run도 같은 판정 규칙으로 run 범위를 명시해 조회한다.
- OCR은 원문 문자열만 중복 제거해 제공한다. confidence, bounding box, storage key는 이번 화면 범위가 아니다.

응답 `data`의 형태는 다음과 같다.

```json
{
  "clip_id": "21",
  "pipeline_run_id": "32",
  "search_applied": false,
  "summary": {
    "total_scenes": 12,
    "captioned_scenes": 12,
    "transcript_scenes": 9,
    "tagged_scenes": 11
  },
  "items": [
    {
      "scene_id": "41",
      "scene_index": 1,
      "start_time_ms": 0,
      "end_time_ms": 4200,
      "representative_frame_timestamp_ms": 1600,
```

## 상태와 오류

- 존재하지 않거나 삭제된 clip, 해당 clip에 속하지 않는 run은 `CLIP_QUERY_404`로 외부에 같은 형태로 감춘다.
- 잘못된 page/size는 기존 `CLIP_QUERY_400`을 사용한다.
- 장면 0건은 404가 아니라 빈 `items`와 0 요약을 반환한다.
- caption, transcript, 대표 프레임, OCR, 태그는 부분 처리 결과에서 각각 독립적으로 비어 있을 수 있다.
- 모든 bigint 식별자는 JSON 문자열로 반환한다.

## 시각 방향

기존 화면의 서리 낀 유리 패널과 청록·남색 팔레트를 유지한다. 새 결과 영역의 특징은 장식이 아니라 `프레임 → 설명 → 대사 → 태그`로 이어지는 검수 흐름이다. 동일한 작은 카드를 반복하지 않고, 각 장면을 가로 행으로 구성해 영상 프레임과 텍스트의 관계를 한 번에 읽게 한다. 데스크톱에서는 대표 프레임을 왼쪽에 고정 폭으로 두고 내용은 오른쪽 정렬선에 맞춘다. 모바일에서는 프레임을 위에 두고 모든 텍스트를 한 열로 쌓는다.
