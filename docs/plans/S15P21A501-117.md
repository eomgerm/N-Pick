이 작업은 `/search/results`의 검색 결과를 **clip이 아닌 scene 단위 Top 10 카드 목록**으로 표현하고, 선택한 scene을 기존 Preview 진입 경계에 넘긴다. 실제 검색 API가 아직 기준 브랜치에 없으므로 mock 데이터로 카드 계약과 목록 동작을 먼저 고정한다. 서버 응답 모델에는 상세 메타데이터를 보존하되 카드에는 제목·키워드·일치도와 썸네일 우하단 장면 구간만 표시한다.

## 4. 카드 표시 모델

`POST /search` DTO를 미리 추측하지 않고, 117에서는 화면에 필요한 display model만 정의한다. 이후 167의 adapter가 서버 DTO를 이 모델로 변환한다.

```ts
interface SearchResultCardModel {
  id: string | number;
  rank: number;
  displayName: string;
  sceneTitle: string;
  sceneStart: number;
  sceneEnd: number;
  broadcastDate: string | null;
  filmedDate: string | null;
  shotType: string;
  sceneType: string;
  imageClass: string;
  imageLabel: string;
}
```

- `id`는 선택과 React key에 쓰는 안정 식별자다. 배열 index를 식별자로 쓰지 않는다.
- `rank`는 mock의 표시 순위를 명시한다. 서버 연동 뒤에는 서버 rank를 그대로 받는다.
- `displayName`은 clip의 사용자용 이름이고 `sceneTitle`과 구분하지만 요약 카드에는 표시하지 않는다.
- 시간 값은 기존 Preview와 호환되는 초 단위를 유지하고 `formatTimestamp()`로 표시한다.
- 날짜는 null을 허용하고 가짜 날짜를 만들지 않는다. 촬영일 필드명은 PRD v6·FRD v3.1의 `filmed_date`에 맞춰 display model에서 `filmedDate`로 쓴다.
- `shotType`과 `sceneType`은 별도 필드로 유지한다. 둘을 하나의 “장면 유형”으로 합치지 않으며 요약 카드에는 표시하지 않는다.
- `sceneType`과 두 날짜는 저장소에서 태그로 표현되고 `shotType`만 scene 컬럼이라는 정본을 transport 구조로 오해하지 않는다. 카드 model은 저장 형태가 아니라 표시 의미만 표현한다.
- 근거·검증·degraded·result ID 등 후속 계약은 기존 mock 모델에 보존할 수 있으나 카드 컴포넌트의 117 필수 props로 끌어오지 않는다.

  - 목록 정렬·필터링
  - Preview open state
  - 서버 응답 검증
  - 근거/검증/degraded 정책

- 결과 목록과 선택된 scene ID를 소유한다.

## 8. 테스트와 수동 확인

### 자동 테스트

- mock 결과가 기본 10건이고 ID와 rank가 중복되지 않는다.
- 모든 scene은 `start < end`이고 total duration 범위 안에 있다.
- 카드 한 장에 thumbnail 대체 설명과 제목, 키워드, 일치도가 렌더링되고 장면 구간은 썸네일 우하단에 한 번만 표시된다.
- display name, 방송일, 촬영일, shot type, scene type은 카드 DOM과 접근성 이름에 렌더링되지 않는다.
- 선택되지 않은 카드와 선택된 카드의 접근성 상태가 구분된다.
- 긴 display name과 type 문자열도 카드 DOM에 노출되지 않는다.

현재 테스트 도구에는 브라우저 DOM 이벤트 환경이 없으므로 React 정적 렌더링과 순수 데이터 검증을 자동화한다. click/Enter/Space → Preview open은 Chrome 수동 시나리오로 검증하며 새 테스트 라이브러리는 추가하지 않는다.

### 수동 시나리오

1. `/search/results?q=...` 기본 조건에서 scene 카드 10개와 순위 1~10을 확인한다.
2. 날짜가 없는 fixture도 필터와 정렬을 깨뜨리지 않는지 확인한다.
3. 각 카드에 제목, 키워드, 일치도가 보이고 장면 구간은 썸네일 우하단에만 한 번 표시되는지 확인한다.
4. 마우스로 임의 카드를 선택하면 해당 scene 제목·시간의 기존 Preview가 열린다.
5. Tab으로 카드에 이동하고 Enter와 Space 각각으로 동일 Preview가 열리며 닫은 뒤 focus가 선택 카드로 복귀하는지 확인한다.
6. 데스크톱 3열, 중간 폭 2열, 좁은 폭 1열에서 10개 카드가 겹치거나 잘리지 않는지 확인한다.
7. `prefers-reduced-motion`에서 hover keyframe animation이 정지하는 기존 규칙이 유지되는지 확인한다.

완료 게이트는 `npm test`, `npm run check`, 기본 mock 10건 렌더링과 카드 선택 Preview 진입 수동 확인이다.

## 10. 선행 조건과 리스크

1. **Jira의 과거 FRD 링크**  
   Jira 본문은 Notion FRD v2.2를 참조하지만 사용자가 `docs/prd.md`와 `docs/frd.md`를 현재 정본으로 확인했다. 구현은 PRD v6·FRD v3.1을 따르고 Notion v2.2는 이력 추적에만 사용한다. 내용이 어긋나면 조용히 혼합하지 않고 현재 저장소 정본을 기준으로 차이를 보고한다.
2. **날짜 상태는 118과 경계가 겹친다**  
   117은 null 날짜의 `미상`만 표시한다. 값은 있으나 unverified인 날짜의 별도 배지·문구와 verified/rejected 체계는 118에 남긴다.
3. **실제 검색 계약 부재**  
   최신 `origin/dev`에는 `POST /search` controller/response DTO가 없다. 117은 display model만 확정하고 endpoint·JSON key·ID 형식을 추측하지 않는다.
4. **기존 demo 데이터를 여러 화면이 공유한다**  
   `demo-scenes.ts`는 검색 결과뿐 아니라 검색 기록과 Preview가 사용한다. 기존 3건의 ID·필드를 깨지 않고 7건을 추가하며 관련 화면 회귀를 확인한다.
5. **후속 브랜치 충돌 가능성**  
   167도 `wireframe-shell.tsx`, `demo-scenes.ts`, `scene-dialogs.tsx`를 건드릴 예정이다. 117을 먼저 merge한 뒤 167이 최신 dev로 rebase하여 카드 model을 소비하는 순서가 가장 충돌이 적다.
