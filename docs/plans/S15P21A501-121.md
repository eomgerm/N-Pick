## 3. 구현 결정

1. 문의 대상 ID는 `sceneId`가 아니라 서버가 저장한 검색 결과의 `resultId`다. 두 값을 같은 `id`로 취급하지 않는다.
2. API DTO와 화면 상태를 분리한다. transport 응답의 `feedbackId`는 FE 모델의 `inquiryId`로 한 번만 변환한다.
3. 서버 응답의 `status`는 현재 계약인 `OPEN`만 접수 성공으로 인정한다. `pending`을 서버 값처럼 가정하지 않는다.
4. 성공 응답에 유효한 문의 ID가 없거나 상태가 다르면 HTTP 2xx여도 성공 표시를 하지 않고 계약 오류로 처리한다.
5. 문의 dialog와 요청 snapshot은 결과 화면이 소유한다. 전역 store나 새 상태관리 라이브러리를 추가하지 않는다.
6. 카드와 Preview의 문의 버튼은 별도 기능이 아니라 같은 결과의 동일 동작을 여는 두 진입점이다. 긍정/부정, 직접 태그 교정, 사유 enum UI는 추가하지 않는다.
7. 자동 재시도는 하지 않는다. 사용자가 명시적으로 재시도할 때만 같은 snapshot과 멱등성 키를 재사용한다.

## 5. API 계약

### 요청

```text
POST /api/v1/search/results/{resultId}/inquiries
Idempotency-Key: <submission.key>
Content-Type: application/json

{}                         // 설명 없음
{ "comment": "..." }     // 설명 있음
```

- `resultId`는 양의 10진 문자열만 허용하고 URL path segment로 안전하게 사용한다.
- comment는 앞뒤 공백을 제거한다. 빈 문자열은 comment 없음과 동일하게 `{}`로 보낸다.
- query, filter, execution, rank, evidence, scene ID, actor ID를 body에 넣지 않는다. 서버가 저장된 결과와 로그인 세션에서 연결한다.
- comment 최대 길이는 현재 BE validation 계약에 없으므로 FE가 임의 제한을 만들지 않는다. UI 안정성을 위한 과도한 입력 상한이 필요하면 BE 계약과 함께 별도로 확정한다.

### 응답

현재 병합된 백엔드 기준 성공 data는 다음과 같다.

```json
{
  "feedbackId": 398021840012345,
  "status": "OPEN"
}
```

FE의 정규화 결과는 다음 형태로 제한한다.

```ts
interface InquirySubmissionResult {
  inquiryId: string;
  status: "open";
}
```

- `feedbackId`는 TSID `long`이므로 JS 안전 정수 범위를 넘을 수 있다. `fetchJson`의 lossless ID 처리에 `feedbackId`를 추가해 원문 10진 문자열로 보존한다.
- 최신 런타임의 JSON reviver source가 없을 때는 safe integer만 문자열로 변환하고 unsafe number는 계약 오류로 거부한다.
- `feedbackId`가 없거나 양의 10진 ID가 아니거나 `status !== 'OPEN'`이면 `ApiClientError('invalid-response')`로 처리한다.
- Jira 121의 `inquiry_id` 표현은 현재 BE의 `feedbackId`와 다르다. 이번 FE 구현은 병합된 BE 계약을 따르고, MR에 이 매핑과 이슈 문구 차이를 기록한다.

## 6. 제출 snapshot과 멱등성

```ts
interface InquirySubmissionSnapshot {
  resultId: string;
  comment: string;
}

interface InquirySubmission {
  key: string;
  snapshot: Readonly<InquirySubmissionSnapshot>;
}
```

1. 사용자가 `문의 접수`를 누르면 현재 `resultId`와 정규화된 comment를 freeze한 snapshot과 새 UUID key를 한 번 만든다.
2. mutation 진행 중에는 카드·Preview·dialog 제출 버튼을 모두 비활성화해 같은 결과의 중복 요청을 막는다.
3. 네트워크 오류, 응답 읽기 실패, 비정상 성공 응답, 5xx처럼 결과가 불확실하면 dialog와 comment를 유지한다.
4. 사용자가 `다시 시도`를 누르면 기존 submission 객체를 그대로 사용해 같은 body와 같은 key를 전송한다.
5. comment를 수정하면 기존 submission을 폐기하고 다음 제출에서 새 snapshot/key를 만든다. 자동으로 재전송하지 않는다.
6. 유효한 ID와 `OPEN`을 받은 뒤에만 result별 상태를 `submitted`로 전환하고 dialog를 닫는다.
7. 이미 접수된 결과의 버튼은 `접수됨`으로 표시하고 비활성화한다. 결과 카드는 목록에서 제거하거나 재정렬하지 않는다.

BE는 현재 헤더가 아니라 결과·사용자 유니크 제약으로 중복을 막는다. 따라서 FE key 재사용은 요청 정체성을 보존하는 클라이언트 계약이며, 같은 key의 payload hash 검증을 서버가 제공한다고 표현하지 않는다.

## 7. 화면 상태 흐름

```text
available
  → dialog-open
      → submitting
          ├─ valid feedbackId + OPEN → submitted
          ├─ ambiguous/transient failure → failed-retryable
          └─ definitive failure → failed

unavailable(snapshot-save-failed)
  → 버튼 비활성 + 가까운 위치에 이유 표시
```

- `available`: 버튼 문구 `이상해요`.
- `dialog-open`: 선택 설명 입력과 “접수 후 즉시 결과가 바뀌지 않음” 안내.
- `submitting`: 문구 `접수 중`, `aria-busy=true`, 재클릭·중복 submit 차단.
- `failed-retryable`: comment 유지, 한국어 실패 안내, `다시 시도` 제공.
- `failed`: 성공처럼 닫지 않으며 오류 코드·request ID는 공통 오류 컴포넌트 정책에 따라 표시.
- `submitted`: 문구 `접수됨`, 성공 live announcement, 자동 개선이 아니라 검수 대기임을 안내.
- `unavailable`: `문의 불가` 또는 disabled `이상해요`와 “검색 기록을 저장하지 못해 문의할 수 없음”을 버튼 가까이에 연결.

dialog 닫기는 요청 전과 실패 후에는 허용한다. 제출 중 닫기로 인해 결과 확인이 불명확해지지 않도록 닫기와 Escape를 잠그거나, Abort 후 동일 submission을 보존하는 한 가지 정책으로 통일한다. 기존 영상 등록과 같은 방식으로 제출 완료까지 잠그는 안을 기본으로 한다.

## 10. 테스트 계획

### 자동 테스트

- API 요청
  - 저장된 양의 `resultId`만 path에 사용
  - 빈 comment는 `{}`, 입력 comment는 trim 후 전송
  - 사용자·query·rank·evidence를 body에 포함하지 않음
  - POST, CSRF 공통 client, Idempotency-Key와 AbortSignal 전달
- 응답 계약
  - 정확한 `feedbackId`와 `OPEN`만 성공
  - 누락 ID, 0/음수, 소수, unsafe number, 다른 상태, body 없는 2xx 거부
  - TSID 정밀도 손실 방지
- 멱등·재시도
  - 같은 submission 재시도는 동일 frozen snapshot/key 사용
  - comment 변경은 새 snapshot/key 생성
  - mutation 진행 중 이중 submit 1회만 호출
  - 실패는 submitted 상태를 만들지 않음
- UI
  - 카드당 문의 버튼 하나와 Preview 진입 유지
  - 카드/Preview의 submitted 상태 동기화
  - 빈 설명 제출 가능
  - 실패 후 comment와 retry 동작 유지
  - snapshot 저장 실패 시 버튼 비활성·사유 노출
  - 성공 뒤 “즉시 자동 개선 아님” 안내

### 통합·수동 시나리오

1. 저장된 정상 검색 결과 카드에서 설명 없이 문의를 제출하고 서버가 반환한 문의 ID를 확인한 뒤에만 `접수됨`이 표시된다.
2. 설명을 입력해 제출하면 comment만 body로 전송되고 검색 context는 서버가 자동 연결한다.
3. 제출 버튼을 빠르게 여러 번 눌러도 요청은 한 번만 전송된다.
4. 네트워크 실패 후 dialog와 comment가 유지되고 `다시 시도`가 동일 Idempotency-Key를 사용한다.
5. 서버 2xx 응답에서 문의 ID가 누락되면 성공으로 표시하지 않는다.
6. snapshot 저장 실패 degraded 결과는 카드와 Preview 모두 문의가 비활성이고 이유가 인접해 보인다.
7. 접수 후 카드가 사라지거나 순서가 바뀌지 않고, 검수 후 반영된다는 안내가 보인다.
8. 키보드만으로 카드 Preview와 문의 버튼을 각각 조작하고 dialog 제출·취소·재시도를 수행할 수 있다.

완료 게이트는 `npm test`, `npm run check`, 그리고 실제 backend를 이용한 제출 성공·실패·비활성 3상태 확인이다.

## 13. 리스크와 확인 사항

1. **실제 검색 result ID 부재**
   -59/-167 전에는 현재 mock 카드가 저장된 `search_result`를 가리키지 않는다. `demo-scenes.id`를 API target으로 간주하지 않는다.

2. **Jira 응답명과 병합된 BE 계약 불일치**
   Jira 121은 `inquiry_id`를 말하지만 현재 BE는 `feedbackId`를 반환한다. 이번 구현은 실제 병합 코드에 맞추되, 팀이 snake_case `inquiry_id`로 계약을 변경하면 API parser 한 곳만 수정한다.

3. **TSID 정밀도**
   `feedbackId`가 JSON number로 오면 일반 `JSON.parse`에서 손실될 수 있다. 성공 여부만 확인한다는 이유로 손실된 ID를 허용하지 않고 공통 client에서 원문 문자열로 보존한다.

4. **Idempotency-Key의 서버 의미**
   FE는 key를 보내지만 BE는 이를 읽지 않는다. 실제 중복 방지는 현재 `(result, actor)` 유니크 정책이다. “같은 key + 다른 payload 409” 같은 보장은 121의 FE 구현 결과로 주장하지 않는다.

5. **불확실한 성공 뒤 comment 변경**
   응답을 받지 못했지만 서버 저장은 성공했을 수 있다. 실패 직후 같은 comment 재시도를 기본 경로로 제공하고, 새 comment 제출을 기존 문의 수정으로 오인하지 않게 안내·정책을 좁게 유지한다.

6. **선행 브랜치 충돌**
   -119는 같은 `wireframe-shell.tsx`, `scene-dialogs.tsx`, CSS를 수정하고 -167은 결과 모델과 shell을 크게 바꿀 예정이다. API/순수 상태부터 구현하고 UI wiring은 선행 병합 후 수행하면 충돌 비용을 줄일 수 있다.
