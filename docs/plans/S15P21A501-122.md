# S15P21A501-122 — Preview 플레이어 구현 기획

## 설명

결과 카드를 선택한 편집기자가 원본 MP4를 해당 장면 시작점부터 확인하고, 전체 영상 안에서 자유롭게 이동하며 선택 구간을 다시 재생할 수 있게 한다. 기존 Preview의 근거·미검증·degraded 표시와 송출 전 확인 고지는 유지한다.

작성일: 2026-09-11. 이 문서는 구현 기획과 현재 검증 상태를 함께 기록한다. 미체크 항목은 선행 연동 또는 실제 환경 검증이 남아 있다. 별도 구현 기획 템플릿이 없어 저장소의 `docs/templates/jira-issue.md`에 있는 설명·작업 내용·제약 조건·참고·완료 조건 구조를 따른다.

위 차이는 구현 기획의 출발점으로 보고한다. 후속 구현에서 공통 플레이어와 실제 문의 상세를 연결했다. 표준 검색 화면을 POST /search에 연결했고 서버 응답의 clip ID와 구간으로 재생한다. 현재 배포 BE는 검색 endpoint가 없어 실제 검색 성공 경로는 아직 검증할 수 없다.

**실행 순서**

1. [ ] 실제 데이터 연결 조건을 먼저 확인한다.
   - 117번 결과 카드와 167번 검색 API 연동의 반영 상태를 확인한다. 현재 126번 기반에는 실제 검색 바인딩이 없으므로, 해당 결과를 가져오는 변경을 선행 반영하거나 합의된 통합 시점에 연결한다.
   - 다른 브랜치의 변경을 임의로 병합하지 않는다. 이 기획의 worktree는 126번 커밋 그대로 분기했다.
   - BE 13번 media endpoint에서 로그인 상태의 원본 MP4와 Range 요청을 실제 확인한다. 문서의 `BE 구현` 표시는 실행 검증 완료와 구분한다.
2. [x] Preview 입력과 미디어 URL 경계를 정의한다.
   - `clipId`와 `sceneId`를 구분한다. 카드 순번, 검색 결과 ID, 표시용 파일명으로 clip ID를 추정하지 않는다.
   - `startTimeMs / 1000`, `endTimeMs / 1000`을 재생용 초 값으로 변환한다. ID는 문자열로 보존한다.
   - 유효한 ID와 `0 <= start < end`의 유한한 구간을 확인한다. 없는 ID·잘못된 구간에는 재생 불가 안내를 제공하고 요청하지 않는다.
   - 기존 `createApiUrl`로 `/media/{clipId}`를 구성하여 `/api/v1` 기본 경로를 보존한다. 서버 경로나 외부 임의 URL을 입력받지 않는다.
3. [x] 기존 dialog 안에 실제 플레이어를 연결한다.
   - 기능 내부 `scene-preview-player.tsx`에 video ref와 재생 이벤트를 모은다. dialog는 메타데이터·문의 액션·포커스를 계속 소유한다.
   - HTML video로 원본을 직접 재생한다. 전체 파일을 fetch해 Blob으로 만드는 방식을 도입하지 않는다.
   - metadata 준비 후 장면 시작점으로 이동하고 초기 seek 완료 후 재생을 시도한다. 0초 장면은 불필요한 seek 완료 이벤트를 기다리지 않는다.
   - 자동 재생이 차단되면 실패로 숨기지 않고 시작점에서 재생 버튼을 제공한다. 재생 중 표시는 `play()` 호출 의도가 아니라 실제 이벤트로 갱신한다.
4. [x] 전체 위치·장면 경계·다시 재생을 연결한다.
   - video의 `currentTime`과 `duration`을 전체 현재 위치/전체 길이로 표시하고, 선택 장면 IN/OUT은 별도로 유지한다.
   - 전체 타임라인에 선택 구간 경계와 현재 위치를 표시한다. duration을 아직 모르면 임의의 전체 길이나 비율을 만들지 않는다.
   - scene end를 넘어도 일시정지·자동 반복하지 않고 원본 끝까지 계속 재생한다.
   - `구간 다시 재생`은 scene start로 이동한 뒤 재생한다. 이후에도 장면 끝에서 멈추지 않는다.
   - 전체 영상 seek와 재생/일시정지를 키보드로 조작할 수 있게 한다. 연속적인 시간 갱신을 live region으로 매번 읽지 않는다.
5. [x] 오류·교체·정리 동작을 구현한다.
   - loading, ready/paused, playing, buffering, error를 실제 video 이벤트로 구분한다. 초기 seek를 기다리는 동안 사용자가 0초를 정상 시작 화면으로 오인하지 않게 한다.
   - 네트워크·재생 형식 문제는 한국어로 안내하고 재시도를 제공한다. 이동 실패는 현재 재생 실패와 구분한다.
   - metadata로 구간과 실제 길이의 불일치를 발견하면 안내한다. 다른 구간이나 0초로 조용히 대체하지 않는다.
   - 닫기·다른 카드 선택·장면 전환 때 이전 재생과 요청을 정리한다. 늦게 끝난 seek/play 이벤트가 새 장면 상태를 덮어쓰지 않게 한다.
   - 기존 dialog의 Escape·포커스 복귀, 근거·경고·문의 가능 여부를 보존한다.
6. [ ] 검증하고 현재 구현 설명을 갱신한다.
   - 단위 검증은 ID/시간 변환과 유효하지 않은 입력에 집중한다.
   - 실제 디코딩 가능한 짧은 MP4와 Range 지원 테스트 서버로 Playwright 재생 검증을 추가한다. 기존 `frontend/e2e`와 mock API 구조를 재사용한다.
   - 실제 BE 연동과 성능 측정은 mock 통과와 별도로 수행한다.
   - `frontend/docs/architecture.md`의 Preview 데모 설명과 `docs/contracts/web-api.md`의 FE 연결 상태를 실제 완료 범위에 맞게 갱신한다.

## 제약 조건

- 새 라이브러리·전역 store·Next.js 미디어 프록시를 추가하지 않는다. 원본 MP4와 브라우저 미디어 기능을 사용한다.
- 성공 응답은 JSON envelope가 아닌 byte다. 브라우저가 seek에 필요한 Range를 요청하게 하고, 서버의 `206`, `Content-Range`, `Accept-Ranges: bytes`를 검증한다.
- 인증은 기존 세션을 따른다. 동일 오리진과 현재 개발 환경의 교차 오리진 경로 모두에서 쿠키 전송을 확인한다. 교차 오리진 사용 시 video의 credentials 설정과 BE CORS가 맞아야 한다.
- video의 error 이벤트만으로 HTTP 상태·서버 JSON 오류 코드를 확정할 수 없다. 파일 누락/권한/서버 장애의 상세 진단은 기존 인증 확인 및 실제 HTTP 관측으로 검증하고, 화면에서는 확인되지 않은 원인을 단정하지 않는다. 세부 원인 표시에 추가 endpoint가 필요하면 계약 협의 사항으로 남긴다.
- 문서상 오류는 `CLIP_404_001/002`, `CLIP_416_001`, `CLIP_500_003`, `CLIP_503_010/011`이다. 서버 메시지나 절대 파일 경로를 그대로 화면에 출력하지 않는다.
- 이슈의 첫 프레임 p95 2초 목표를 검증한다. 선택 시점부터 선택 장면 위치의 실제 프레임 표시까지 측정하며 metadata 수신이나 seek 시작을 첫 프레임으로 세지 않는다.
- 측정 제안: 동일 클립 집합·브라우저·네트워크에서 첫 로드와 재진입을 각각 최소 30회 기록하고 p95와 실패 횟수를 따로 보고한다. 가능한 경우 `requestVideoFrameCallback`으로 목표 위치 프레임을 확인한다. 자동 재생 차단은 별도 기록한다. 이는 측정 방법 제안이며 제품 AC를 추가하는 것은 아니다.
- `Cache-Control: private, no-store` 계약을 유지한다. warm 측정은 같은 세션에서의 재진입으로 정의하고 HTTP 캐시 재사용을 가정하지 않는다.
- 검색·문의 기능 전체 구현, 검수 처리 기능 확장, 영상 변환·HLS·다운로드 기능은 이 이슈 범위에 포함하지 않는다. 단, 실제 검색 결과에서 Preview로 이어지는 통합 검증 없이는 이슈 완료로 판단하지 않는다.

## 완료 조건

공통 플레이어와 실제 검색 응답 바인딩을 완료했다. 실제 미디어 성능은 검증용 BE에서 측정했으며, 전체 검색 E2E는 현재 배포 BE의 검색 API 및 처리된 장면 부재로 미완료다. 아래 표는 제품 인수 기준이다.

| 검증 | 기대 결과 |
| --- | --- |
| 실제 결과 카드에서 중간 장면 선택 | 해당 clip ID로 요청하고 scene start에서 재생; ms→초 변환 확인 |
| 0초 장면·소수 초 장면 | 초기 seek 대기로 멈추지 않고 올바른 위치로 진입 |
| 전체 위치와 선택 구간 | 현재 시간/원본 길이와 IN/OUT을 함께 표시 |
| scene end 경과 | 경계를 표시하며 원본 재생을 계속함 |
| 구간 다시 재생 | 장면 시작으로 복귀하고 실제 재생함 |
| 영상 내 seek | 브라우저 Range 요청 및 서버 206/Content-Range 확인 |
| 자동 재생 차단 | 수동 재생 가능, 허위 재생 중 표시 없음 |
| 누락 파일·재생 불가·이동 실패 | 한국어 안내·재시도, 검색 빈 결과로 바뀌지 않음 |
| 닫기·빠른 카드 교체·재진입 | 이전 소리·이벤트가 남지 않으며 올바른 장면과 포커스 복원 |
| ID 없는 공통 호출·잘못된 구간 | 임의 media 요청과 가짜 재생 성공 없음 |
| 근거·미검증·degraded·송출 전 고지 | 실제 재생 중에도 유지 |
| 인증 및 경로 | 세션 기반 접근, 원본 절대 경로 미노출 |

**2026-09-11 실제 연동 검증 결과**

- 표준 /search/results는 SearchResults → POST /search → 응답 검증 → 카드 → clipId 기반 Preview 순서로 연결했다. 검색 실패는 데모로 바꾸지 않는다. 같은 조건 수동 재시도, 추가 근거와 degraded 표시도 유지한다.
- 배포 중인 localhost:8080: 제공된 편집자 계정 로그인 200. POST /api/v1/search 404, 기존 clip의 GET /api/v1/media/{clipId}도 404. DB는 기존 clip 1건, scene 0건이다. 원래 서버/DB 데이터는 변경하지 않았다.
- 현재 브랜치 backend/Dockerfile로 별도 검증 이미지를 빌드하고 localhost:8182에서 실행했다. DB 연결은 읽기 전용, 미디어 볼륨도 읽기 전용, Flyway 비활성. 이 서버는 기존 MP4에 206, Accept-Ranges: bytes, Content-Range: bytes 0-1023/1173383, Cache-Control: private, no-store를 반환했다.
- 대상: 기존 clip 885423794805527772. H.264, 1248×704, 3.041667초, 1,173,383 bytes. 새 원본·장면·계정을 생성하지 않았다.
