# 인터페이스 계약 — 리졸버 API (서비스 서버 ↔ 질의 리졸버)

서비스 서버가 발신자다. 검색 한 건의 동기 예산(p95 10초) 안에서 끝나며 재시도가 없다([README](README.md) 「왜 문서를 나누는가」의 비교 표).

## 1. 범위

이 문서가 지금 정하는 것은 `POST /query/tokenize` 하나다.

`POST /query/resolve` 의 HTTP 계층(주소·요청 형식·오류 코드)은 **아직 쓰지 않았다.** 출력 JSON 키와 schema 는 이미 확정돼 있고 정본은 `ai/src/npick_worker/query_resolver/schema.py`(`query-resolver/v2`)다. 그 파일이 스스로 정본임을 적고 있으므로 여기에 옮겨 적지 않는다. HTTP 계층까지 문서화할지는 별건으로 판단한다.

**이 문서의 라우트에는 도메인 오류 코드가 없다.** 실패가 요청 검증 하나뿐이고 본문은 FastAPI 기본 형식이라 붙일 코드가 생기지 않는다. 앞으로 필요해지면 검색·리졸버 API 가 이미 점유한 `SRCH_` 접두를 쓰고 새로 만들지 않는다.

## 2. `POST /query/tokenize`

규칙 적용 뒤의 확장어를 후보 조회용 토큰으로 바꾼다. 쓰임새는 S15P21A501-48 확정 계약 7 — 「확장어 토큰화는 원 질의와 같은 Kiwi 설정·전처리를 쓴다」다.

**이 라우트가 따로 있는 이유.** 교정(`patch_parse`)으로 검수자가 추가한 확장어는 리졸버가 모르는 값이라 `/query/resolve` 응답에 토큰을 실어 보내는 방식으로는 덮이지 않는다. 백엔드에는 Kiwi 가 없다.

규칙 기반이라 LLM·DB·임베딩을 부르지 않는다. 같은 입력은 언제나 같은 출력이다.

### 2.1 요청

```json
{ "texts": ["귀성객", "부산 침수", "···"] }
```

| 필드 | 형식 | 제약 |
| --- | --- | --- |
| `texts` | 문자열 배열 | 최대 **64** 항목, 항목당 최대 **200** 자 |

상한은 실측 근거가 없는 보수값이다. 이 라우트가 동기 검색 예산 안에서 돌고 Kiwi 분석 비용이 총 글자 수에 비례하는데, `expanded_terms` 에는 개수 상한이 없고 교정으로 검수자가 직접 넣을 수도 있어 입력이 무제한이기 때문이다. 정본은 `npick_worker.query_api.MAX_TOKENIZE_ITEMS` · `MAX_TOKENIZE_TEXT_LENGTH` 다.

### 2.2 응답

```json
{
  "tokens": [["귀성객"], ["부산", "침수"], []],
  "normalization_version": "query-norm/v1:b0d96c0c:kiwi0.23.2:model0.23.0"
}
```

| 필드 | 형식 | 의미 |
| --- | --- | --- |
| `tokens` | 문자열 배열의 배열 | `texts` 와 **같은 길이·같은 순서** |
| `normalization_version` | 문자열 | 토큰 경계를 결정한 설정과 엔진의 식별자 |

입력 문자열을 되돌려 주지 않는다. 호출부가 보낸 것을 그대로 갖고 있으므로 위치로 맞춘다.

### 2.3 상태 코드

| 코드 | 언제 |
| --- | --- |
| `200` | 정상. **토큰이 0 개인 항목이 있어도 200 이다** |
| `422` | 요청 검증 실패 |

**400 을 내는 자리가 없다.** 토큰이 하나도 안 나오는 항목(기호뿐인 확장어 등)은 오류가 아니라 빈 배열이고, 요청 전체를 깨뜨리지 않는다. S15P21A501-48 계약 9 가 「확장어 부재·토큰화 실패는 degraded 가 아니다」로 닫아 두었다 — 확장어 한 건 때문에 검색을 끊으면 안 된다.

**422 는 상한 초과만이 아니다.** 필드 누락·타입 불일치도 같은 코드로 온다. 본문은 FastAPI 기본 형식이다.

```json
{ "detail": [ { "type": "too_long", "loc": ["body", "texts"], "msg": "..." } ] }
```

| `detail[].type` | 뜻 |
| --- | --- |
| `too_long` | 항목 수가 §2.1 의 상한을 넘겼다 |
| `string_too_long` | 항목 하나의 글자 수가 상한을 넘겼다 |
| `missing` · `tuple_type` · `string_type` | 호출부가 만든 요청이 스키마와 다르다 |

422 를 전부 「상한 초과」로 읽으면 직렬화 버그가 조용히 확장어 없는 검색으로 나타난다. 가르려면 이 필드를 봐야 한다.

**상한 초과는 끊어 보내면 된다.** 항목끼리 독립이라 64개씩 나눠 두 번 부르면 전량 손실을 피할 수 있다. 그렇게 하지 않기로 했다면 확장어 없이 검색을 이어간다 (계약 9).

### 2.4 불변식

1. **`normalization_version` 은 `/query/resolve` 응답의 같은 이름 필드와 같다.** 두 값이 다르면 그 토큰과 그 검색은 서로 다른 규칙으로 만들어진 것이다. `tests/test_query_api.py::test_tokenize_version_matches_resolve` 가 고정한다.
2. **색인 측과 같은 토큰이다.** `korean_tokens.index_tokens` 하나를 쓰며 `ocr` 단계가 같은 함수를 쓴다.
3. **별칭·불용어·정렬을 걸지 않는다.** 그것들은 지문(`normalized_query`) 전용이다. 색인이 하지 않는 변형을 질의에만 걸면 오류 없이 0 건이 된다. 확장어는 이미 별칭 확장의 결과이기도 하다.
4. **`len(tokens) == len(texts)`** 이고 순서가 보존된다.
