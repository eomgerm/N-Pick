# OCR 화면 글자 품질 하네스 (S15P21A501-260)

QA 가 화면의 `꿀꺽` 을 `꿀찍` 으로 읽은 사례를 보고해 만들었다. **검출·인식 설정을
바꾸면 여기로 회귀를 잰다.**

**워커 런타임이 아니다** — 배포 이미지에 들어가지 않는다. 다만 `npick_worker.ocr` 를
**import 한다**: 실제 설정(`config/ocr.v1.toml`)·실제 backend·실제 후처리를 거치지
않으면 측정이 무의미하기 때문이다(`eval/query_resolver/` 와 같은 판단).

## 왜 재현율이 아니라 정확일치인가

`docs/ocr.md` §2·§5 의 "재현율 27/37" 은 **사람이 출력을 보고 "이건 읽어 낸 것" 으로
센** 수치다. 그 세는 방식에서 `올림픽 G-1년 페스티벌` → `-립픽G-1년페스티벌` 은 정답
쪽에 들어간다. 사람 눈에는 읽어 낸 것이 맞다.

**검색에는 아니다.** `ocr_observation.tokens` 는 이 원문을 Kiwi 로 자른 결과이고
(`docs/ocr.md` §6), 한 글자가 어긋나면 그 문구로 들어온 질의는 **0 건**이 된다. 티켓의
제약 "검색 근거로 OCR 토큰이 쓰이므로 품질이 검색에 영향" 이 가리키는 자리가 이것이고,
`꿀꺽` → `꿀찍` 도 검출·인식은 성공했고 글자만 틀린 사례다.

**색인 토큰에서 끝나지도 않는다.** `vlm_metadata/grounding.py` 가 OCR `rawText` 를
장면 설명 프롬프트에 그대로 넣는다(정본 설정 `vlm_metadata.v2.toml` 에서 켜져 있다).
오독은 검색 토큰과 **사용자에게 보이는 장면 설명** 양쪽에 들어가고, `unverified`
표시는 앞쪽에만 붙는다. 자세한 것은 `docs/ocr.md` §12.

그래서 라벨 문구 하나의 결과를 셋으로 가른다.

| 판정 | 뜻 | 검색 |
| --- | --- | --- |
| `exact` | 비교값이 같다 | **이것만 이어진다** |
| `misread` | 읽기는 했는데 글자가 다르다 | 못 찾는다. 게다가 **틀린 토큰이 색인에 들어간다** |
| `miss` | 대응하는 관측이 없다 | 못 찾는다 |

비교값은 `npick_worker.ocr.merge.comparison_text` 그대로다(NFKC·casefold·공백 제거).
병합이 "같은 문구인가" 를 판정하는 규칙과 평가가 "맞게 읽었는가" 를 판정하는 규칙이
다르면 한쪽을 고칠 때 다른 쪽이 조용히 어긋난다. **원문은 건드리지 않는다** — 여기서
만드는 정규화 문자열은 판정용이고 저장되는 값이 아니다(`docs/ocr.md` §3).

### 지표

| 이름 | 정의 |
| --- | --- |
| `exact` / `legible` | **주 지표.** 사람이 확실히 읽을 수 있는 문구 중 정확히 읽은 수 |
| `misread` / `miss` | 실패의 두 갈래. 어느 쪽이든 그 문구로는 검색되지 않는다 |
| `silentMisread` | 오독 중 `unverified` 표시가 **붙지 않은** 것. `min_confidence` 를 넘겨 그대로 검색 토큰이 된다. 이 티켓이 실제로 줄여야 하는 수 |
| `hallucination` | **글자가 아예 없는 프레임**에서 나온 출력. `docs/ocr.md` §2 의 "명백한 오탐" 과 같은 정의다 |
| `unmatched` | 어느 라벨에도 붙지 못한 관측 전체. 판정하지 않고 세기만 한다 — 늘어나면 색인에 근거 없는 토큰이 늘어난다는 신호다 |
| `cer` | 라벨 문구 전체 기준 문자 오류율. **누락은 전부 오류로 센다** |
| `cerMatched` | 읽어 내기는 한 문구들만의 문자 오류율 |

`partial`·`illegible` 라벨은 점수에 들어가지 않지만 **짝짓기에는 참여한다.** 자기
관측을 데려가지 않으면 그 관측이 오탐 자리에 남는다(`samples/README.md` 가 "재현율에서
제외하고 오탐으로도 세지 않는다" 로 정한 것).

### `misread_floor` 감도

닮은 정도가 이 값 미만인 쌍은 오독이 아니라 누락으로 센다. 기본 `0.34`.

**주 지표는 이 값과 무관하다** — 비교값이 같아야 `exact` 이고 그 판정에 문턱이 끼지
않는다. 이 값이 가르는 것은 실패를 어느 쪽으로 셀지 뿐이다.

| floor | `base` exact / 오독 / 누락 | 후보 exact / 오독 / 누락 |
| --- | --- | --- |
| 0.20 | 16 / 13 / 8 | 24 / 8 / 5 |
| 0.30 | 16 / 13 / 8 | 24 / 8 / 5 |
| **0.34** | **16 / 13 / 8** | **24 / 8 / 5** |
| 0.40 | 16 / 11 / 10 | 24 / 7 / 6 |
| 0.50 | 16 / 11 / 10 | 24 / 6 / 7 |
| 0.60 | 16 / 10 / 11 | 24 / 5 / 8 |

0.20~0.34 는 판정이 완전히 같고 0.40 부터 경계 쌍이 누락 쪽으로 넘어간다. **더 낮춰도
달라지지 않는 구간의 위쪽 끝**을 골랐다. `--floor-sweep` 이 이 표를 다시 만든다.

## 환경

**별도 venv 가 필요 없다.** `eval/query_resolver` 와 달리 이 하네스가 부르는 것은
런타임 의존(rapidocr·onnxruntime)뿐이라 프로젝트 venv 에서 그대로 돈다.

지표 함수의 단위 테스트는 모델 가중치도 샘플도 없이 돈다.

```bash
uv run --directory ai pytest tests/test_ocr_eval_metrics.py
```

실제 측정에는 라벨된 클립의 keyframe 이 필요하다. 영상은 커밋하지 않으므로
(`ai/.gitignore`) 로컬에서 먼저 뽑는다.

```bash
uv run --directory ai python -m npick_worker.frame_extraction.report \
    samples/KNI_02205.mp4 --out samples/out/KNI_02205-frames
```

# 기본 설정 한 번

## 사례 등록부

`cases.json` 은 QA 가 보고한 개별 오독과 같은 유형으로 재현된 사례를 붙잡아 둔다.
**라벨 파일이 이미 덮는 문구는 여기 적지 않는다** — 같은 것을 두 곳에 적으면 한쪽만
고쳐진다. 여기 있는 것은 라벨된 클립 **밖에서** 나온 사례다.

```bash
# 등록부의 프레임만 읽는다. 라벨된 클립이 없어도 돈다
uv run --directory ai python eval/ocr/ocr_bench.py --cases-only --variant all
```

| 상태 | 뜻 |
| --- | --- |
| `fixed` | 이제 정확히 읽는다 |
| `reproduced` | 보고된 오독이 그대로 나온다 |
| `changed` | 여전히 틀리는데 다르게 틀린다. **고쳐진 것이 아니다** |
| `absent` | 읽기는 했는데 그 문구의 관측이 없다. 오독이 아니라 누락으로 바뀌었다 |
| `not-in-run` | 이 측정이 그 프레임을 보지 않았다. **`absent` 와 다르다** |
| `frame-missing` | 등록부에 `frame` 이 없다. 아직 재현할 자료가 없는 사례다 |

`expected` 를 사람이 적지 않았으면 `labeledBy` 에 그렇게 적는다. AI 예비 라벨을 사람
검수 Gold Set 처럼 쓰지 않기 위해서다(`samples/README.md` 의 같은 구분).

**프레임이 붙은 세 건에 20개 변형을 전부 걸어 봤고 `fixed` 는 한 칸도 없다.** 근거와
해석은 `docs/ocr.md` §12 다.

**등록부가 가리키는 keyframe 은 커밋되지 않는다**(영상에서 나온 것이라 `ai/.gitignore`
가 막는다). 클론 직후에는 `--cases-only` 가 돌지 않고, 그 표본을 먼저 뽑아야 한다.
경로 오타는 `tests/test_ocr_eval_metrics.py` 가 표본이 있을 때만 잡는다.

## 한계

- **표본이 클립 한 편이다.** `KNI_02205`(800x450, keyframe 23장, legible 문구 37개)가
  이 저장소에 사람이 적은 라벨이 있는 유일한 클립이다. 여기의 모든 수치가 그 표본
  안에서만 참이고, `docs/ocr.md` §11 의 "1080p 로 전부 다시 잰다" 가 그대로 유효하다.
- **짝짓기는 탐욕법이다.** 닮은 순서대로 집는다. 최적 매칭과 갈릴 수 있고, 갈리는 쌍은
  `misread_floor` 근처의 쓰레기다.
- **`unmatched` 는 판정하지 않는다.** 글자가 있는 프레임에서 라벨에 안 붙은 관측이
  오독인지, 라벨이 놓친 문구인지, 사람도 못 읽는 글자인지 이 하네스는 모른다.
- **장당 시간은 장비 부하에 민감하다.** onnxruntime 이 코어를 다 쓰므로 다른 작업이
  도는 동안 재면 같은 입력이 몇 배까지 느려진다(`docs/ocr.md` §9 의 같은 주의).
  한 번의 `--variant all` 로 돌리는 것만으로는 부족하다 — **그 패스가 도는 동안 장비에
  다른 것을 올리지 않아야** 줄 사이 비교가 성립한다. 위 표에 시간 열이 없는 이유다.
- **모델 자체는 바꾸지 못했다.** 한국어 인식 모델은 `korean_PP-OCRv5_rec_mobile` 뿐이고
  server 판이 없다(`docs/ocr.md` §12). 여기서 비교할 수 있는 것은 검출 쪽과 전처리다.
- **사례 등록부는 점수가 아니다.** 상태 네 값이지 지표가 아니고, 등록된 사례가 무작위
  표본도 아니다. "몇 건이 `fixed` 인가" 를 품질 수치로 쓰지 않는다 — 그건 위 표가 한다.

## 파일 이름에 대해

지표 모듈이 `metrics.py` 가 아니라 `ocr_metrics.py` 다. `eval/query_resolver/metrics.py`
와 이름이 겹치면 `pyproject.toml` 의 `mypy_path` 에 두 디렉터리가 함께 올라갈 때 mypy 가
앞엣것 하나만 `metrics` 로 해석해 **다른 하네스를 검사하고 통과시킨다.**
