# 고유명사 검색 오탐 — 재현과 원인 분류 (S15P21A501-293)

QA(2026-09-22)가 올린 고유명사 오탐 3건을 각각 재현하고 원인을 갈랐다. **세 건의 원인이
전부 다르다.** 한 건은 리졸버 프롬프트, 한 건은 dense 채널 설정, 한 건은 색인 토큰 형식이고
고치는 층도 필요한 배포 절차도 서로 다르다. 그래서 이 문서는 조사 기록이고, 수정은 아래
§5 의 분리 티켓이 각각 가져간다.

측정 기준점:

| | 값 |
| --- | --- |
| dev | `ab83c5c1` (S15P21A501-279·-278·-234 모두 머지된 상태) |
| `tokenizer_version` | `query-norm/v1:b0d96c0c:kiwi0.23.2:model0.23.0:encpos2` |
| `prompt_version` | `query-resolver-prompt/v2:b98a0418` |
| 리졸버 모델 | GMS `gpt-4o-mini` |
| 측정일 | 2026-09-23 |

재현은 전부 **워커 프로세스 안에서** 했다. `POST /search` 를 부르지 않았다 — 그 호출은
`search_execution` 에 행을 남겨 같은 날 도는 평가 QA 기록과 섞인다
(`eval/search/README.md` 의 경고와 같은 이유다).

## 1. 경부선·호남선 → 폭포

**재현: 질의 측에서는 재현되지 않는다. 원인은 dense 채널이다.**

토큰화와 해석 둘 다 정상이다.

```
"경부선"                  -> search_tokens ('경부선/nnp',)
"호남선 기차 지나가는 장면"  -> search_tokens ('호남선/nnp','기차/nng','지나가/vv','장면/nng')

리졸버("경부선"):
  locations: [{type: facility, value: "경부선", origin: explicit_query, confidence: 1.0}]
  expanded_terms: []
```

`경부선` 은 Kiwi 가 NNP 한 토큰으로 잡고 문맥이 바뀌어도 흔들리지 않는다(§3 의 표 참고).
리졸버도 고유명사를 그대로 시설로 두고 상위 개념으로 바꾸지 않는다. **S15P21A501-279 와
무관하고 리졸버 문제도 아니다.**

남는 경로는 dense 뿐이다. 후보 출처는 두 개뿐인데(`SearchCandidatePipeline.rank`) —
BM25(`caption_tokens`·`transcript_tokens`·OCR `tokens`)와 dense — **태그는 후보를 만들지
않고 점수만 매긴다.** `경부선` 이 어느 캡션·자막·화면 글자에도 없으면 BM25 가 0 건이고,
그러면 dense 후보가 10 칸을 전부 채운다. `FalseHitGuardPolicy` 는 날짜 충돌만 제외하므로
의미가 먼 장면을 걸러 주지 않는다. 그 자리를 막는 유일한 장치가 dense 관련성 하한선
(S15P21A501-278)이다.

**확인할 것은 그 하한선이 실제 배포에서 걸려 있는가 하나다.** 기본값이 두 군데에서 다르다.

| 자리 | 값 | 뜻 |
| --- | --- | --- |
| `application.yml` | `SEARCH_DENSE_MAX_DISTANCE:2.0` | 코사인 거리 전 범위 — **아무것도 거르지 않는다** |
| `compose.yaml` | `${SEARCH_DENSE_MAX_DISTANCE:-0.75}` | 278 이 실측으로 정한 하한선 |

배포 서버의 `.env` 가 이 값을 덮고 있으면 compose 기본값이 안 걸린다. 저장소만으로는
판정할 수 없다.

**확인 방법 (서버 접근이 있는 사람이 한다).** 해당 질의를 한 번 돌리고
`search_execution` 의 설정 스냅샷에서 `dense-search/v2` 의 `maxDistance` 를 읽는다.
2.0 이면 하한선이 꺼진 것이고, 0.75 인데도 폭포가 나오면 값 조정 대상이다.

## 2. 둘리 → 「캐릭터」

**재현: 그대로 재현된다. 원인은 리졸버 프롬프트에 캐릭터를 담을 칸이 없는 것이다.**

```
리졸버("둘리"):
  intent: "unknown"
  entities: []   locations: []   classifications: []   incident_names: []
  expanded_terms: ["캐릭터", "만화"]
  confidence: 0.0
```

`config/query_resolver.v2.toml` 의 배정 규칙이 배열마다 담을 것을 닫아 두었다 — 규칙 7 은
entities 에 사람·기관만, 8 은 locations 에 장소·시설만, 9 는 classifications 에
계절·날씨·장면유형만 허용한다. **캐릭터·작품명·브랜드를 담을 배열이 없다.** 그래서 규칙 11
(「동의어와 관련 검색어는 expanded_terms 에만」)로 흘러가고, 원 고유명사는 구조화 출력에서
통째로 사라진다. QA 가 본 「캐릭터」가 그 결과다.

원 고유명사가 항상 사라지는 것은 아니다.

```
리졸버("둘리 나오는 장면"):
  expanded_terms: ["둘리"]        # 살아남되 확장어로 강등된다
  intent: "scene_search", confidence: 0.8
```

둘 다 anchor 가 아니라서 구조화 축 점수에 기여하지 못한다. 그리고 `matched_keywords` 는
확장어도 함께 싣되 origin 으로 구분하므로(S15P21A501-234), 화면에는 「캐릭터」가 확장어로
붙는다.

**BM25 는 `둘리/nnp` 를 그대로 보낸다.** 결과에 둘리가 없는 것은 질의가 그 말을 잃어서가
아니라 색인에 그 말이 없기 때문일 수 있다 — 확장어 `캐릭터` 로 다른 장면이 걸려 올라오는
것은 확실하지만, 「둘리는 없고」 쪽은 색인 내용을 봐야 갈린다.

수정은 프롬프트 한 층이고 **재색인이 필요 없다.** 다만 프롬프트를 바꾸면
`eval/query_resolver/gold.json` 200문항 결과가 함께 움직이므로 before/after 를 재야 한다
(`eval/query_resolver/README.md`).

## 3. 사람 이름 — S15P21A501-279 가 만든 회귀

**재현: 재현된다. 그리고 279 이전에는 없던 문제다.**

Kiwi 는 사전에 없는 사람 이름의 **품사를 문맥에 따라 다르게 준다.** 형태는 같다.

```
"김예은"                        -> ('김예은', 'NNG')   # 사용자가 치는 검색어
"오늘 김예은 씨가 인터뷰를 했다"   -> ('김예은', 'NNP')   # 자막에 색인되는 형태
```

279 이전 인코딩은 `형태` 뿐이라 둘이 같은 토큰이었다. 279 가 `형태/품사` 로 바꾸면서
`김예은/nng` 와 `김예은/nnp` 가 되었고, `paradedb.term_set` 은 정확 일치라 **영영 안 맞는다.**
`korean_tokens` 모듈 주석이 경고하는 「검색이 0 건」이 품사 태그 때문에 사람 이름에서
일어난 것이다.

**실측.** 흔한 성 30 × 흔한 이름 20 = 600 개를 만들어, 검색어로 친 형태와 자막 문장
(`"오늘 {이름} 씨가 인터뷰를 했다"`) 안의 형태가 토큰을 하나라도 공유하는지 셌다.

| 색인 인코딩 | 매칭되는 이름 | 비율 |
| --- | --- | --- |
| `형태` (279 이전) | 529 / 600 | **88.2%** |
| `형태/품사` (`encpos2`, 현재 dev) | 209 / 600 | **34.8%** |

실패 391 건을 원인별로 가르면:

| 원인 | 건수 | 비율 |
| --- | --- | --- |
| 형태는 같은데 품사 태그만 다름 | 320 | 53.3% — **279 가 만든 것** |
| 토큰 경계 자체가 다름 | 71 | 11.8% — 279 이전에도 있던 것 |

경계가 갈리는 쪽은 더 나쁘다. 음절이 사라지고 흔한 낱말로 바뀐다.

```
"배현진" 단독      -> 배/NNP + 현/MM + 진/NNG -> 토큰 ('배/nnp','진/nng')
                     MM(관형사)은 keep_pos 에 없어 '현' 이 통째로 사라진다.
                     남은 토큰은 배(과일)·진(陣) 이라 엉뚱한 장면에 걸린다.
"오늘 배현진 씨를"  -> 배현진/NNP

"박지훈" 단독      -> 박/NNP + 지훈/NNP
"박지훈 선수가"     -> 박지훈/NNP
```

**사전에 있는 말은 흔들리지 않는다.** 이 불안정은 사전 밖 고유명사에 한정된다 — 아래는
같은 낱말을 다섯 가지 문장 틀에 넣어 품사를 비교한 것이다.

| 낱말 | 관측된 품사 |
| --- | --- |
| 경부선 · 호남선 · 전라선 · 둘리 · 뽀로로 · 이태원 · 한강 · 청와대 | `nnp` 하나뿐 |
| 중앙선 · 폭포 · 국회 · 지하철 · 고속도로 · 태풍 · 폭설 | `nng` 하나뿐 |
| 서울역 | 문장 안에서는 `서울`+`역` 으로 쪼개져 단독 토큰이 사라진다 |

### 고치는 방향과 그 비용

`encode_token` 에서 **NNG 와 NNP 를 한 품사류로 합치면** 된다. 279 가 막으려던 것은
명사와 용언 어간의 충돌(`비`=rain NNG vs `비다` VV 어간)이지 명사끼리의 충돌이 아니었다.

```
NNG·NNP -> 'n' 으로 합친 인코딩:
  사람 이름 매칭   527 / 600 = 87.8%   (279 이전 88.2% 를 사실상 회복)
  "비 오는 날"     {'비/n', '날/n', '오/vv'}
  "빈 교실"        {'교실/n', '비/vv'}
  겹침             없음                 (279 가 막으려던 오탐은 그대로 막힌다)
```

**이 변경은 `_ENCODING_VERSION` 을 올리고 저장 토큰 전체 재색인을 요구한다.** 색인과 질의가
서로 다른 판으로 돌면 검색이 0 건이 되므로 재색인과 배포가 원자적이어야 한다 — 279 가 방금
같은 작업을 했다. 평가 QA(2026-09-23) 당일에는 넣지 않는다.

남은 11.8%(경계 분절)는 이 변경으로 해결되지 않는다. 그쪽은 사용자 사전이나 색인 측
n-gram 이 필요한 별개 문제이고, `config/query_normalization.v1.toml` 이 인물 사전을 일부러
넣지 않은 근거(성만으로 동일인을 보장할 수 없고 사전이 계속 늙는다)를 다시 판정해야 한다.

## 4. 세 건이 공유하지 않는 것

QA 가 한 덩어리로 올렸지만 층이 다르다. 한 티켓에서 같이 고치면 어느 변경이 무엇을 고쳤는지
측정이 섞인다.

| | 고치는 층 | 재색인 | 측정 하네스 |
| --- | --- | --- | --- |
| 경부선 → 폭포 | BE 설정 (`SEARCH_DENSE_MAX_DISTANCE`) | 불필요 | `eval/search` |
| 둘리 → 캐릭터 | 리졸버 프롬프트 (`query_resolver.v*.toml`) | 불필요 | `eval/query_resolver` |
| 사람 이름 | 색인 토큰 형식 (`korean_tokens.encode_token`) | **필요** | `eval/search` |

## 5. 이 문서가 남기는 후속 작업

1. **경부선 → 폭포.** 배포 서버의 실효 `maxDistance` 를 확인하고, 하한선이 켜져 있는데도
   재현되면 값을 조정한다. `eval/search` 로 전후를 잰다.
2. **둘리 → 캐릭터.** 프롬프트에 캐릭터·작품명·브랜드의 자리를 만들거나, 배정할 배열이 없는
   고유명사를 확장어로 보내더라도 **원 고유명사를 함께 보존**하게 한다.
   `eval/query_resolver/gold.json` 200문항 before/after 를 첨부한다.
3. **사람 이름.** NNG·NNP 를 합친 인코딩으로 올리고 재색인·배포를 원자적으로 한다.
   평가 QA 이후. `tests/test_korean_tokens.py` 의 xfail 두 건이 이 작업의 인수 조건이다 —
   고쳐지면 `strict=True` 라 XPASS 로 실패하므로 표시를 함께 지운다.
