# scene detection 선정과 설정

FRD `F-03` 장면 분할 구현 근거. 구현은 `src/npick_worker/scene_detection/`.

## 1. 라이브러리·모델 비교

뉴스 영상 기준으로 후보를 넷 놓고 봤다.

| | PySceneDetect (선정) | TransNetV2 | AutoShot | ffmpeg `select=gt(scene,N)` |
| --- | --- | --- | --- | --- |
| 방식 | 프레임 간 HSV 차이(`content`) / 이동 평균 대비 상대 변화(`adaptive`) | CNN 기반 shot boundary 검출 | TransNetV2 계열 재학습 | ffmpeg 내장 scene score |
| hard cut | 강함 | 강함 | 강함 | 보통 |
| 디졸브·와이프 | **약함** (점진 전환을 놓친다) | 강함 (이 모델의 존재 이유) | 강함 | 약함 |
| 모델 가중치 | 없음 | 필요 (수십 MB) | 필요 | 없음 |
| 의존성 | `scenedetect-headless` + `av`. opencv-headless·numpy 를 끌어온다 (설치 기준 약 160MB) | torch — `gpu` 그룹 opt-in 성질을 깬다 | 동일 | **시스템 ffmpeg 설치 필요** |
| 결정론 | 완전. 같은 파일·같은 설정이면 동일 | 가중치·torch 버전까지 고정해야 성립 | 동일 | 결정론적이나 후처리를 직접 짜야 함 |
| 최소 장면 길이 | 내장 (`min_scene_len`) | 없음 — 직접 구현 | 없음 | 없음 |
| 임계값 조정 | 파라미터로 노출 | 재학습 또는 후처리 임계값 | 동일 | scene score 하나뿐 |

### 왜 PySceneDetect 인가

1. **실측 근거가 아직 없다.** 지금 필요한 건 최고 정확도가 아니라 **측정 대상이 될 조정 가능한 기준선**이다.
   임계값을 돌려가며 개발셋을 볼 수 있어야 나중에 근거를 갖고 확정한다(FRD §11).
2. **GPU 선택 의존성을 지킨다.** `ai/AGENTS.md` 는 "GPU 없이도 워커가 기동하는 성질을 깨지 않는다"를 규약으로 둔다.
   TransNetV2 는 torch 를 기본 그룹으로 끌어올리거나 scene detection 을 GPU 필수로 만든다. 1단계가 치명 단계라 후자는 곧 GPU 없으면 파이프라인 전체 정지다.
3. **뉴스는 hard cut 이 지배적이다.** 앵커 ↔ 현장 ↔ 인터뷰 전환은 대부분 컷이다. 디졸브는 코너 전환과 b-roll 몽타주에 몰린다.
   1번 샘플에서 실측한 비율도 hard cut 10 대 디졸브 3 이다. **다만 그 디졸브 3개를 전부 놓친다**(§4.4).
4. **재시도 멱등성**(모듈 재현성 계약)이 공짜다. 가중치 해시·torch 버전·연산 결정론을 관리할 필요가 없다.

### 언제 다시 볼 것인가

**조건은 이미 충족됐다.** 1번 샘플에서 디졸브 3곳을 전부 놓쳤고(§4.4), **임계값 조정으로는
고칠 수 없음**이 같이 확인됐다 — 디졸브를 잡으려면 `threshold ≤ 7.8` 이어야 하는데 컷이 아닌
카메라 무빙의 최고값이 20.5 라 반드시 과분할한다. 파라미터가 아니라 방식의 한계다.

그래도 이번 티켓에서 바꾸지 않는 이유는 위 1·2·4 가 그대로 살아 있기 때문이다. 실측 전에
필요한 건 조정 가능한 기준선이고, 재현율을 실제로 개선하는지는 Gold Set 없이 말할 수 없다.
**교체 판단의 근거 자료가 이제 생겼다**는 것이 이번 측정의 결과다.

교체할 때는 TransNetV2 를 `SceneDetector` Protocol (`scene_detection/detector.py`) 뒤에 두 번째
구현체로 붙인다. 상위 코드는 바뀌지 않는다. 그때는 가중치 해시를 그 구현의 `version` 에
섞는다 — Protocol 이 이미 그 자리를 갖고 있다(§2).

세 후보의 정확도 순위는 논문·벤치마크에 있지만 **뉴스 도메인 수치는 우리 Gold Set 으로만 말할 수 있다.**
근거 없는 숫자를 이 문서에 옮겨 적지 않는다(FRD §8.2 — 수치·장비·표본을 임의로 새로 만들지 않는다).

### 디코드 백엔드를 PyAV 로 고정한 이유

PySceneDetect 는 OpenCV 와 PyAV 백엔드를 모두 지원하고 기본값은 환경에 따라 갈린다.

- PyAV 휠에 ffmpeg 이 번들되어 있어 **시스템 ffmpeg 설치가 필요 없다.**
- 백엔드가 환경마다 다르면 같은 파일에서 프레임 수와 타임스탬프가 달라질 수 있다. 멱등성이 깨진다.

`scenedetect` 는 PyAV 만 쓰더라도 임포트 시점에 `cv2` 를 요구한다. 그래서 headless OpenCV 를 쓴다 —
`opencv-python`(GUI 포함)이면 컨테이너에서 `libGL.so` 로 죽는다.

0.7 부터 이 선택 방법이 바뀌었다. `[opencv-headless]` **extra 가 없어지고** headless 변종이
`scenedetect-headless` **별도 배포판**이 됐다. 그래서 의존성은 `scenedetect-headless` 로 선언하고,
임포트 이름은 그대로 `scenedetect` 다. 두 배포판을 동시에 설치하면 같은 임포트 이름을 다투므로
한쪽만 선언한다.

## 2. 설정과 버전

정본: `src/npick_worker/config/scene_detection.v1.toml`. **임계값을 코드에 두지 않는다.**

| 키 | 의미 | 비고 |
| --- | --- | --- |
| `schema` | 설정 스키마 이름 | `version_id` 앞부분 |
| `detector` | `content` \| `adaptive` | `adaptive` 는 핸드헬드·빠른 팬 오탐이 적다 |
| `min_scene_len_ms` | 컷 사이 간격과 꼬리 scene 의 하한 | 플래시·1~2프레임 튐 흡수. **흡수는 scene 이 2개 이상일 때만 돈다** — 컷이 없는 짧은 영상은 그 길이의 scene 하나가 나온다 |
| `downscale` | 분석 해상도 배율. `1` = 원본 | `auto` 를 쓰지 않는다 — 해상도마다 값이 달라지면 클립 간 비교가 깨진다 |
| `frame_skip` | 건너뛸 프레임 수 | `0` 이 아니면 경계가 그 배수로 거칠어진다 |
| `content.threshold` | HSV 차이 임계값 | 스케일이 `adaptive` 와 다르다 |
| `content.luma_only` | 색 무시, 밝기만 | 흑백 아카이브용 |
| `adaptive.adaptive_threshold` | 이동 평균 대비 비율 | `content.threshold` 와 단위가 다르다 |
| `adaptive.min_content_val` | 이 값 미만은 컷 후보에서 제외 | |
| `adaptive.window_width` | 이동 평균 창 크기 | |

`SceneDetectionConfig.version_id` = `<schema>:<정규화 JSON 의 sha256 앞 8자리>`.
선택되지 않은 detector 의 파라미터까지 해시에 넣는다 — 파일 하나가 통째로 설정 단위이고,
detector 를 바꾸면 당연히 다른 version 이어야 하기 때문이다.

이 값은 **scene detection 단계의 몫**이다. FRD `pipeline_run.pipeline_version` 은 파이프라인 전체
값이므로 여러 단계의 버전을 묶는 일은 S15P21A501-70 에서 한다.

설정을 바꾸려면 이 파일을 `v2` 로 복사하고 아래 §4 에 근거를 남긴다. v1 을 그 자리에서 고치면
과거 결과의 `version_id` 가 무엇을 뜻했는지 알 수 없게 된다.

### 재현 조건은 세 필드 튜플이다

`version_id` 는 **설정 파일만** 해시한다. 설정을 그대로 두고 라이브러리를 올려도 경계가 달라질
수 있으므로 `version_id` 하나로는 재현을 보장하지 못한다. 그래서 결과에 구현 버전도 함께 싣는다:

| 축 | 필드 | 값 예시 | 무엇이 바뀌면 변하는가 |
| --- | --- | --- | --- |
| 설정 | `SceneDetectionResult.config_version` | `scene-detect/v1:20dfc0a6` | toml 값 |
| 구현 | `SceneDetectionResult.engine` / `engine_version` | `pyscenedetect` / `0.7.1` | 라이브러리·모델 버전(가중치 해시 포함) |

> 재현성 식별자: `(config_version, engine, engine_version)` (모듈 재현성 계약)

같은 입력과 같은 재현성 식별자는 같은 분할 결과를 만든다.

`engine_version` 은 하드코딩하지 않고 설치된 배포판에서 읽는다. 하드코딩하면 휠과 조용히
어긋나는데, 그게 바로 재현성 기록이 거짓이 되는 경로다.

`version_id` 의 정의는 "설정 파일의 해시"로 **유지한다.** 라이브러리 버전을 여기에 섞으면
v1/v2 config 버저닝이 무의미해진다 — 설정을 안 바꿨는데 버전 이름이 달라지기 때문이다.

## 3. 실측 후 확정으로 미룬 항목

전부 `scene_detection.v1.toml` 의 잠정값이며 개발셋 측정 전에는 근거가 없다.

| 항목 | 현재 잠정값 | 확정에 필요한 것 |
| --- | --- | --- |
| `content.threshold` | 27.0 (라이브러리 기본값) | 뉴스 클립 Gold Set 의 컷 시각 대비 precision/recall |
| `min_scene_len_ms` | 1000 | 검색 단위로서 유의미한 최소 길이. 너무 길면 짧은 인서트 컷이 사라진다 |
| `detector` 선택 | `content` | 샘플 6번(핸드헬드)에서 `adaptive` 와 비교 |
| `downscale` | 1 | 처리 시간 대비 정확도 손실 측정 (FRD §8.2 처리 속도) |

참고 실측: 색만 다른 합성 프레임의 `content_val` 은 20 근처로 기본 임계값 27 을 넘지 못한다.
구조까지 바뀌면 70~90 이 나온다. 테스트 픽스처가 단색이 아니라 줄무늬·노이즈 패널을 쓰는 이유다
(`tests/conftest.py`).

## 4. 샘플 확인 결과

확보한 샘플은 1번(표준 리포트) 하나다. 2번(앵커 고정 샷)은 스포츠뉴스 소스에 컷 없는 30초가
거의 없어 별도 클립을 구하는 대신 1번의 정지 구간에서 확인했다(§4.3). 3번(전환 효과)은 **이 클립이
그 역할을 했다** — 디졸브가 3곳 들어 있다(§4.4). 4~8번은 미확보.

출처는 AI Hub 017 한국어 텍스트-비디오-사운드 데이터(스포츠뉴스, 라이선스 KBS, 2017-02-09 방송분).
영상과 라벨 JSON 은 커밋하지 않는다(`ai/.gitignore`). **라벨에 샷 경계는 없다** — `video.term` 은
발화 구간이다. 컷 정보는 이 문서의 측정이 유일한 출처다.

아래 수치는 **`pyscenedetect 0.7.1`** 에서 측정했다. 처음 `0.6.7.1` 로 측정한 뒤 라이브러리를
올려 같은 클립을 다시 돌렸는데 **scene 수·경계 ms·`duration_ms` 가 전부 동일했다** — 즉 이
기준선은 두 버전에 걸쳐 재현된다. 그래도 §2 의 두 번째 축이 필요한 이유는, "이번엔 같았다"가
"항상 같다"를 뜻하지 않기 때문이다.

### 4.1 산출 결과

| 클립 | expected_cut_count | 산출 scene 수 | 과분할 지점 | 미분할 지점 | detector / threshold |
| --- | --- | --- | --- | --- | --- |
| `KNI_02205` (76.1s, 800×450, 30fps CFR) | 미측정 — 손으로 세지 않았다 (독립 측정으로는 13, §4.4) | 10 | 없음 | **4곳 — 디졸브 3 · 하드컷 1 (§4.4)** | `content` / 27.0 |

- `version_id` = `scene-detect/v1:20dfc0a6`
- 경계(ms): 0 · 39467 · 45733 · 48600 · 52400 · 56100 · 59133 · 62867 · 71100 · 73100 → 76067
- 검출된 9개 경계는 **전부 실제 hard cut 이 맞다**(§4.4 에서 육안 확인). 과분할은 없다.
- **재현율 9/13 ≈ 69%.** 정밀도는 9/9.
- **디코드·ms 변환 검증**: AI Hub 라벨의 `metadata.length` 76.066s 대 산출 `duration_ms` 76067
  → 1ms 차. 프레임 번호 기반 타임코드가 이 CFR 소스에서 정확하다.

`expected_cut_count` 는 비워 둔다. §4.4 의 13 은 손으로 센 값이 아니라 같은 영상을 다른 방법으로
측정한 값이다. 독립 정답이 아니므로 정답 칸에 넣지 않는다.

### 4.2 임계값 스윕 — 검출된 경계는 안정적이지만 여유는 좁다

`content.threshold` 를 27 → 20 → 15 → 12 → 9 → 6 으로 내려가며 봤다. 39.5s 이후 경계 8개 중
**7개는 ms 까지 완전히 고정**이고, 나머지 하나(`62867`)만 `threshold=6` 에서 `62833` 으로
1프레임(34ms) 움직인다. 임계값을 아슬아슬하게 넘긴 약한 경계가 아니라 강한 hard cut 이라는 뜻이다.

임계값을 내리면 경계가 사라지는 대신 **늘어난다**: 27에서 10개 → 20에서 12개 → 12에서 16개 →
6에서 21개. 27 이 놓치고 있는 후보가 있다는 뜻이므로, 확정할 때는 이 추가 경계들이 실제 컷인지
과분할인지 갈라야 한다 — §4.4 가 그 작업이다.

프레임별 `content_val` 분포:

| 구간 | 중앙값 | p95 | 최고 | 27 초과 |
| --- | --- | --- | --- | --- |
| 0 ~ 39.5s | 1.8 | 8.6 | 20.5 | 없음 |
| 39.5s ~ | 1.3 | 11.7 | 83 | 8개 (50·54·57·57·59·62·66·83) |

검출된 컷은 50~83 이고 컷이 아닌 카메라 무빙의 최고점은 20.5 다. 이 둘만 보면 27 이 넓은
골짜기 안에 있는 것처럼 보이지만 **그렇지 않다.** `66.70s` 의 하드컷이 **26.61** 이다(§4.4).

> 실제 여유는 **0.39**. 골짜기가 아니라 벼랑 끝이다.

`detector = "adaptive"` 로 바꾸면 11개(+1). 이 클립은 삼각대 고정 샷 위주라 두 detector 를
가르지 못한다.

### 4.3 정지 구간 — 2번(고정 샷) 대체 확인

`scene 0` 이 0~39.467s 로 클립의 절반이다. 이 안에 27 을 넘는 프레임이 하나도 없다(최고 20.5).

**이걸 "39초짜리 고정 샷에서 과분할이 없다"로 읽으면 안 된다.** 그 구간은 고정 샷이 아니다 —
디졸브 2개(19.17s, 33.10s)와 카메라 무빙이 들어 있다(§4.4). 컷이 없어서 안 나뉜 것이 아니라
**컷이 있는데 못 잡은 것**이다.

진짜 정지 구간은 **0 ~ 17s** 다. 이 17초는 1초·3초 간격 델타도 8~21 에 머문다(§4.4 의 지연 델타).
2번 샘플이 확인하려던 것 — 촬영 노이즈·압축 아티팩트·미세한 흔들림이 임계값을 넘기지 않는다 —
은 이 17초에서 확인됐다. 39초가 아니다.

### 4.4 놓친 컷 4개 — 실측

`content_val` 은 **인접 프레임만** 본다. 변화가 여러 프레임에 흩뿌려지면 총량이 아무리 커도
임계값을 넘지 않는다. 그래서 인접 델타에 더해 **지연 델타**(1초·3초 간격)를 같이 쟀다.

지연 델타가 25 를 넘는 국소 최대를 전환 후보로 잡고, 후보마다 두 가지로 갈랐다:

- **블렌드 잔차** `r = mean|F(t) − blend(A,B,α)| / mean|F(t) − A|`
  디졸브는 정의상 두 정지 화면의 선형 혼합이므로 `r` 이 작다. 카메라 무빙은 `A` 와 `B` 가
  공간적으로 어긋나 blend 가 이중상이 되고 어느 실제 프레임과도 안 맞는다 → `r` 이 1 근처.
- **α 곡선** — `F(t)` 를 `A→B` 축에 사영한 계수. 디졸브는 매끄러운 단조 증가, 하드컷은 계단.

검증용 HSV 델타 구현은 `scenedetect` 의 `content_val` 과 소수점까지 일치시켰다
(프레임 720→721 = 19.92, 양쪽 동일). 아래 수치는 threshold 27 과 직접 비교할 수 있다.

**놓친 컷 (전부 육안 확인 완료)**

| 시각 | 프레임 | 최대 인접차 | `r` | α | 유형 | 장면 |
| --- | --- | --- | --- | --- | --- | --- |
| 19.17s | 568–582 | 9.31 | 0.165 | 매끄러운 0→1 | 디졸브 | 리포터 → 바이애슬론 체험 부스 |
| 33.10s | 986–1006 | 7.82 | 0.163 | 매끄러운 0→1 | 디졸브 | 컬링 부스 → 야외 건물 |
| 36.10s | 1076–1089 | 18.16 | 0.214 | 매끄러운 0→1 | 디졸브 | 야외 건물 → 페스티벌 게이트 |
| **66.70s** | 2000 | **26.61** | 0.413 | **0→0.99 한 프레임** | **하드컷** | 눈조각 광장 와이드 → 눈조각 클로즈업 |

**컷이 아닌 것 (현재 동작이 정답)**: 22.93s · 26.87s · 28.53s · 42.60s · 75.63s — 전부 `r` 0.67~0.76.
카메라 무빙이다. 그중 24.07s 는 이 클립에서 컷이 아닌 구간의 최고값(20.53)을 낸다.

두 가지가 확인됐다.

**1. 디졸브 약점은 임계값으로 못 고친다.** 디졸브 3개의 최대 인접차는 7.82 · 9.31 · 18.16 이다.
전부 잡으려면 `threshold ≤ 7.8` 이어야 하는데 컷이 아닌 카메라 무빙의 최고값이 20.53 이다.
**디졸브를 잡는 순간 무빙까지 전부 잡혀 과분할한다.** 파라미터 조정이 아니라 방식의 한계이고,
§1 "언제 다시 볼 것인가"의 조건이 이걸로 충족됐다.

**2. `content_val` 은 색 분포가 비슷한 하드컷을 못 본다.** 66.70s 는 구도가 완전히 바뀌는
명백한 컷인데 26.61 이다. 두 샷 다 흐린 하늘 아래 흰 눈이라 HSV 분포가 거의 안 움직인다.
`threshold` 를 21~26 으로 내리면 이 컷은 잡히고 무빙(20.53)은 안 잡히지만, **클립 하나로는
확정 근거가 되지 않는다**(§3, FRD §11). 여유가 0.39 라는 사실만 기록한다.

### 4.5 확인 절차

**1단계 — 산출 결과와 멱등성**

```bash
uv run --directory ai python -m npick_worker.scene_detection.report \
    samples/KNI_02205.mp4 --out samples/out/KNI_02205
```

`samples/out/<이름>/scene-*.png` 이 실제 컷 지점인지 눈으로 본다. 같은 인자로 두 번 돌려
`scenes.json` 이 바이트 단위로 같은지도 함께 본다(모듈 재현성 계약).

**2단계 — 놓친 컷 (필수)**

1단계로는 **놓친 컷을 원리적으로 찾을 수 없다.** `report.py` 는 검출된 scene 의 시작 프레임만
뽑으므로, 못 잡은 경계는 PNG 에 아예 나타나지 않는다. §4.4 의 4개도 그래서 처음에 못 봤다.

놓친 컷은 이렇게 찾는다:

1. 전 프레임의 **1초·3초 간격 델타**를 잰다. 인접 델타는 작은데 지연 델타가 25 를 넘는 지점이
   전환 후보다 (디졸브·와이프는 변화를 여러 프레임에 나눈다)
2. 후보마다 **블렌드 잔차 `r`** 과 **α 곡선**으로 디졸브 / 하드컷 / 카메라 무빙을 가른다
3. 후보 구간을 3×3 컨택트 시트 PNG 로 뽑아 **육안으로 확정한다.** 수치와 시트가 엇갈리면
   시트를 따른다 — 잔차는 모델이고 시트는 원본이다

델타 계산은 `scenedetect` 의 `content_val` 과 값이 일치하는지 먼저 확인한다. 안 맞으면
임계값 27 과 비교할 수 없다.
