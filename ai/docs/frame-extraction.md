# frame extraction 선정과 설정

FRD `F-03` 프레임 추출 구현 근거. 구현은 `src/npick_worker/frame_extraction/`.

만들어야 하는 것은 FRD가 정한 두 가지다 — **장면의 복수 키프레임**과 **결과 카드에 쓸 대표
이미지 1개**(`docs/frd.md:121`). 잡 API 쪽 규약(입력·키·순서)은
[../../docs/contracts/job-api.md](../../docs/contracts/job-api.md) §4.3.1이 정본이고, 이
문서는 **왜 이렇게 뽑는가**를 적는다.

## 1. 스키마가 정한 것과 정하지 않은 것

이 단계의 설계 여지는 대부분 `keyframe` 테이블이 이미 좁혀 놓았다.

```sql
CREATE TABLE "keyframe" (
    "keyframe_id" bigint NOT NULL,
    "scene_id"    bigint NOT NULL,
    "timestamp_ms" bigint NOT NULL,
    "storage_key" text   NOT NULL,
    CONSTRAINT uq_keyframe_scene_timestamp UNIQUE (scene_id, timestamp_ms)
);
```

| 요구 | 스키마의 자리 | 결과 |
| --- | --- | --- |
| scene과의 연결 | `scene_id` | 워커는 `scene_index`로 보내고 BE가 TSID를 발급한다 |
| 이미지 위치 | `storage_key` | 파일명만 단계가 정하고 접두는 잡 레이어가 붙인다 |
| 대표 이미지 1개 | **없음** | 목록 **순서**로 전달한다 (§2) |
| 축소 thumbnail | **없음** | 만들지 않는다. 카드용 축소는 조회 시점의 몫 (§4) |
| 같은 프레임 두 번 금지 | `UNIQUE(scene_id, timestamp_ms)` | 중복 제거 단위가 **프레임 번호**여야 한다 (§5) |

## 2. 대표 이미지를 순서로 표현하는 이유

`keyframe`에 `is_representative` 같은 칸이 없고, ERD 주석이 "결과 목록의 대표 이미지는 첫
장을 쓴다"로 두었다. 셋 중 하나를 골라야 했다.

| 안 | 내용 | 판단 |
| --- | --- | --- |
| 목록 순서 (선택) | 대표를 첫 원소로 보내고 BE가 그 순서대로 INSERT → 대표 = 최소 `keyframe_id` | 스키마 변경 없음. ERD 주석의 "첫 장"이 그대로 성립한다 |
| `timestamp_ms` 최소 | "첫 장"을 시각 순으로 해석 | **선정이 사라진다.** 장면 시작 프레임은 디졸브 잔상·암전이 걸리기 쉬운 자리다 |
| 컬럼 추가 | `is_representative` + 부분 유니크 인덱스 | 가장 명시적이지만 ERD 정본·baseline 마이그레이션·BE 엔티티를 함께 고쳐야 한다 |

순서로 정한 대신 **`representativeTimestampMs`를 payload에 함께 싣는다.** 규약이 순서 하나에
매달려 있으면, 나중에 누가 `timestamp_ms` 순으로 정렬해 저장하는 순간 대표가 조용히 바뀐다.
값을 같이 보내면 BE가 저장 직전에 대조할 수 있다.

## 3. 무엇을 좋은 프레임으로 보는가

선명도는 **라플라시안 분산**이다. 초점이 맞고 윤곽이 살아 있는 프레임에서 크고, 모션 블러·
디졸브 중간·단색 화면에서 작다. 뉴스 화면의 자막·슈퍼는 고주파 성분이 강해 이 값이 큰 쪽으로
몰리는데, 그것이 OCR 대상으로도 대표 이미지로도 원하는 방향이다.

**휘도 표준편차를 따로 본다.** 암전·화이트아웃이 선명도만으로는 걸러지지 않기 때문이다. 단색
프레임의 라플라시안도 0에 가깝지만, 잡음이 조금 섞이면 흐릿한 실사 프레임보다 높게 나올 수
있다. 표준편차가 `min_luma_std` 미달이면 후보에서 뺀다.

**미학적 점수나 학습된 가중치를 쓰지 않는다.** 그런 기준은 개발셋 측정 없이 고를 수 없고
(FRD §11), 지금 필요한 것은 "블러·암전을 피한다"까지다. 슬롯의 후보가 전부 블랭크면 그중
선명도 최고를 `blank=True`로 쓴다 — 치명 단계이므로 keyframe 0장으로 끝내는 것이 블랭크 한
장보다 나쁘다. 다만 그 사실을 지우지 않고 `metrics.blankKeyframes`로 보고한다.

### 뽑는 순서

1. **슬롯 계획** (`selector.plan_slots`) — 장면을 `interval_ms`로 나눠 장 수를 정하고
   `[min, max]`와 **창 안의 프레임 수**로 자른다. 경계에서 `edge_margin_ms`를 뺀 창을 등분해
   각 칸의 **중앙**을 슬롯 중심으로 둔다. 끝을 쓰면 첫 슬롯이 창 시작에 붙어 여백을 둔 의미가
   없어진다. 여백을 빼면 서로 다른 프레임이 `min_keyframes_per_scene`개도 남지 않는 장면에서는
   여백을 포기한다(§7).
2. **후보 전개** — 슬롯 중심에서 `candidate_step_ms`씩 좌우로 번갈아 벌린다. 순서가 중심에
   가까운 순이고, 그것이 곧 동점 규칙이다.
3. **프레임 변환** — 목표 ms를 프레임 번호로 옮기고 장면 안으로 당긴다(§5).
4. **측정** (`pyav_backend.measure`) — 후보만 디코드해 선명도·휘도를 잰다.
5. **선정** (`selector.select`) — 슬롯마다 블랭크가 아닌 것 중 선명도 최고. 이미 다른 슬롯이
   고른 프레임은 다시 고르지 않는다.
6. **정렬** (`selector.order_for_output`) — 대표(선명도 최고, 동점이면 이른 시각)를 맨 앞으로.
7. **쓰기** (`pyav_backend.write`) — 고른 프레임만 원본 해상도 JPEG으로.

선정 규칙(1·2·5·6)에 영상이 필요 없는 것이 의도다. "몇 장을 어디서 뽑고 무엇을 대표로
하는가"는 백엔드 라이브러리와 무관하게 표로 검증된다. 1번은 프레임레이트를 **인자로** 받는다 —
그 값을 알아내는 일이 백엔드의 몫이고, 그 값으로 무엇을 정하는지는 선정의 몫이다. fps는 검증
표의 한 열이 될 뿐이라 영상 픽스처는 여전히 필요 없다.

### 남은 어긋남 — 적응형 keyframe(FR-PRC-012)의 자리

**이 구현은 장 수·위치를 `interval_ms`와 균등 슬롯으로 정한다. 내용 기반 적응형이 아니다.**
현재 정본인 FRD F-03이 "장면의 복수 키프레임"만 요구하기 때문이고(`docs/frd.md:121`), AGENTS.md
기능 개발 절차가 "AC에 없는 기능을 임의로 추가하지 않는다"이므로 여기까지가 이 티켓의 범위다.

다만 정본이 갈리는 지점이라 이력을 남긴다.

- `581f6e3`(2026-09-02, 이 티켓 `S15P21A501-91`)이 당시 저장소 FRD(v2.2)의 `FR-PRC-012`에
  적응형 선택과 초기 파라미터를 정의했다 — 균등 후보 5개(0/25/50/75/100%) 중 중앙을 시드로
  시작해, 나머지를 이미 고른 keyframe과 비교하여 변화량이 임계(~12, HSV 히스토그램 코사인거리)
  이상일 때만 추가한다. 정적 장면 1~2장·동적 장면 3장 이상, 장면당 평균 ~2.0장.
- `fb68230`(2026-09-07, `S15P21A501-154`)이 `docs/frd.md`를 Notion 정본 최신판(v3.1)으로
  통째로 교체하면서 그 문단이 사라졌다. v3.1 머리말의 작성일은 09-04이고 추적표(§10.2)는
  `FR-PRC → F-03~04, F-14 / 처리·재시도 유지`로만 적는다. **적응형을 폐기했다는 결정은 v3.1
  어디에도 없고**, §11.2는 "기능 범위가 줄어든 것은 군중 밀도 하나"라고 적는다. 반면 같은
  §10.2가 "모든 옛 세부 조항의 무변경 승계를 뜻하지 않는다"고 못 박으므로, 형식상 현재 정본에
  적응형 요구는 없다.
- 되살릴 때 초기 파라미터를 그대로 쓸 수는 없다. 후보 위치 `0%`·`100%`는 장면 경계에 후보를
  놓는데 그것이 `edge_margin_ms`가 피하는 전환 잔상 구간이고, `100%`는 반열린 구간 밖이다.
- 두 방식은 최적화 대상이 다르다. 적응형은 **장 수·위치를 내용으로** 정해 정적 장면의 중복을
  줄이고, 지금 구현은 **뽑은 자리에서 프레임 품질을**(선명도·블랭크) 보장한다. 장면당 평균은
  이미 비슷하다 — 적응형의 목표가 ~2.0장이고 샘플 실측이 2.3장이므로(§9) 쟁점은 총량이 아니라
  분배다. 그래서 둘은 배타적이지 않고, 적응형으로 자리를 잡고 그 근방에서 선명도로 프레임을
  확정하는 조합이 가능하다.

정본을 정하는 일은 이 저장소가 아니라 FRD 쪽이므로 별도 티켓으로 분리한다. 그 결정 전에는
이 문서와 계약 §4.3.1이 말하는 "간격 + 선명도"가 구현의 정본이다.

## 4. 원본 해상도 JPEG 하나만 저장한다

FRD는 "작은 글자를 읽을 때는 축소된 대표 이미지 대신 원본 해상도의 프레임을 사용한다"
(`docs/frd.md:131`)를 요구한다. 그래서 **다운스케일하지 않는다.** 이 자산의 1차 소비자는 사람
눈이 아니라 OCR이다.

축소본 파일은 만들지 않는다. **담을 컬럼이 없다** — `keyframe.storage_key`는 하나뿐이고
`clip`에도 thumbnail 칸이 없다. 결과 카드용 축소는 ID 기반 조회 응답에서 만들 수 있으므로
저장이 필요 없다. `stages.py`의 2단계 필수 출력 문구가 "복수 keyframe·thumbnail"인 것과
어긋나는 지점이라 계약 문서 §4.3.1에도 적어 두었다.

### 품질(qscale) 실측

샘플 클립(`KNI_02205`, 800x450)에서 실제로 뽑은 **keyframe 23장 평균**이다(§9와 같은 집합).
프레임 몇 장만 재면 화면 내용에 따라 20% 넘게 흔들리므로 같은 집합으로 고정한다. ffmpeg
mjpeg의 qscale은 2가 최고, 31이 최저이고 0~100 척도가 아니다.

| qscale | 프레임당 | 23장 합 | 1080p 환산 |
| --- | --- | --- | --- |
| **2 (기본)** | 73 KiB | 1,675 KiB | 약 420 KiB |
| 3 | 57 KiB | 1,301 KiB | 약 325 KiB |
| 5 | 42 KiB | 955 KiB | 약 240 KiB |
| 8 | 30 KiB | 691 KiB | 약 175 KiB |
| 12 | 23 KiB | 526 KiB | 약 130 KiB |

기본값을 2로 두는 이유는 작은 글자 인식률에 낼 만한 비용이라고 봤기 때문이다. **다만 이것도
실측 후 확정 대상이다** — OCR 정확도와 qscale의 관계는 개발셋으로만 말할 수 있다.

### 인코딩에서 실측으로 걸러낸 것 셋

세 가지가 "그럴듯하지만 틀린" 선택이었다. 셋 다 조용히 잘못되므로 적어 둔다.

1. **`stream.options`의 `q:v`·`qscale`은 아무 일도 하지 않는다.** ffmpeg **CLI**의 옵션이라
   libavcodec에 닿지 않는다. 넘겨도 파일 크기가 기본값 그대로였다. 품질은
   `codec_context.qmin/qmax`로 준다.
2. **`yuvj420p`는 프레임마다 폐기 경고를 찍는다.** `yuv420p` + 색 범위 JPEG이 같은 뜻이지만,
   **변환 시점에도 목표 범위를 줘야 한다.** 인코더에만 주고 `reformat`에 주지 않으면 swscaler가
   기본 범위로 변환해 바이트가 달라졌다. 둘 다 주면 `yuvj420p` 경로와 sha256까지 같다. 밝기
   범위가 좁아지면 어두운 화면의 작은 글자가 먼저 뭉개지므로 이 동일성은 OCR 품질 문제다.
3. **인코더 스레드 수가 산출 바이트를 바꾼다.** mjpeg는 스레드 수에 따라 슬라이스를 나눈다.
   같은 프레임이 1스레드에서 72,991 B, 4스레드 이상에서 74,599 B였고 sha256도 달랐다. 기본값
   (auto)은 CPU 코어 수를 따라가므로 **개발 머신과 GPU 파드의 결과가 달라진다.** 스레드를 1로
   고정했다.

컨테이너는 `image2`가 아니라 `mjpeg` 원시 muxer를 쓴다. `image2`는 파일명에 `%03d` 같은 시퀀스
패턴이 없다고 프레임마다 경고를 두 줄씩 찍고(장면 수백 개면 수천 줄이다), 두 경로의 산출
바이트는 같았다.

## 5. ms와 프레임 번호

변환 규칙은 `npick_worker.timecode` 하나다. `scene_detection`이 경계를 ms로 만들고 이 단계가
그 ms를 다시 프레임 번호로 되돌리므로, 두 단계가 같은 규칙을 쓰지 않으면 keyframe이 자기 scene
밖의 프레임을 가리킨다.

- `frames_to_ms`는 **반올림**이다(원래 `scene_detection`에 있던 함수를 공용 모듈로 옮겼다).
- `ms_to_frame`은 그 **역함수**여야 하므로 역시 반올림이다. 내림으로 두면 30fps에서
  `frames_to_ms(1) = 33`인데 `ms_to_frame(33) = 0`이 되어, scene 시작 시각이 **직전 scene의
  마지막 프레임**을 가리킨다.
- 가장 가까운 프레임이므로 정규 시각이 목표보다 최대 반 프레임(30fps면 17ms) 앞이나 뒤일 수
  있다. 반열린 구간의 양 끝에서 그것이 옆 구간으로 새지 않게 보정하고 **구간 안의 프레임을
  세는** 일은 `timecode.frames_in_range`가 한다. 빈 구간을 scene의 실패로 번역하는 것만
  `frames_in_span`이 한다 — 그 구간이 scene이라는 것을 아는 쪽이 거기다.
- 세는 규칙이 한 곳에 있어야 하는 이유는 선정도 그것을 쓰기 때문이다. "이 창에서 몇 장을 뽑을
  수 있는가"를 두 곳에서 따로 세면 한쪽이 ms로, 다른 쪽이 프레임으로 세는 어긋남이 생긴다.

**중복 제거의 단위는 프레임 번호다.** 서로 다른 두 ms가 같은 프레임을 가리킬 수 있으므로
(10fps면 100ms 안의 모든 ms가 한 프레임이다) ms로 중복을 없애면 같은 화면이 두 장 저장되고,
`UNIQUE(scene_id, timestamp_ms)`는 그것을 막지 못한다. 저장하는 `timestamp_ms`도 목표 시각이
아니라 **그 프레임의 정규 시각**이다.

## 6. 디코드를 두 번 하는 이유

`measure`(후보 측정)와 `write`(고른 프레임 쓰기)가 각각 순차 디코드를 한 번 한다. 한 번으로
끝내는 방법이 둘 있지만 지금은 쓰지 않는다.

| 방법 | 비용 |
| --- | --- |
| 두 번 디코드 (선택) | 디코드 2회. **후보**를 들고 있지 않는다 — 메모리는 한 프레임, 디스크는 쓸 장 수뿐이다 |
| 후보를 메모리에 들기 | 장면당 `max_keyframes × candidates_per_slot`장을 원본 해상도로 쥔다 |
| 후보를 전부 인코드 후 삭제 | 쓸 장 수의 **세 배**를 디스크에 쓴 뒤 지운다 |

파드 디스크는 휘발성이고 한 파드가 잡을 여러 개 처리한다. 후보 때문에 상한이 3배로 늘어나지
않는 편을 골랐고, 필요해지면 `FrameGrabber` Protocol 뒤에서 바꿀 수 있다 — 상위 코드는 바뀌지
않는다.

**다만 "디스크 상한이 입력과 무관하다"는 것은 후보 전략에만 참이고 저장하는 keyframe에는
거짓이다.** 실제 상한은 `scene 수 × max_keyframes_per_scene × 장당 크기`이므로 클립이 길고
장면이 많으면 함께 커진다 — 1080p·qscale 2 기준 장당 약 420 KiB(§4)이므로 장면 100개면
약 200 MiB다. 잡 레이어가 올린 파일을 즉시 지우지만(`jobs/runner.py`의 `_upload`) **그것으로
피크가 내려가지는 않는다** — `write`가 그 클립의 JPEG 전부를 쓴 뒤에야 업로드가 시작하기
때문이다. 줄어드는 것은 점유 시간이다. 피크를 실제로 낮추려면 scene 단위로 쓰고 올려야
하고, 그건 `FrameGrabber`와 `StageOutcome.uploads`의 모양을 바꾸는 일이라 §10에 남긴다.

**탐색(seek)하지 않는다.** 탐색은 키프레임 정렬 때문에 원하는 프레임을 놓칠 수 있고
(`scene_detection/report.py`의 같은 판단), 컨테이너 GOP 구조에 따라 결과가 달라지면 멱등성이
깨진다.

## 7. 설정과 버전

정본: `src/npick_worker/config/frame_extraction.v1.toml`. **임계값을 코드에 두지 않는다.**

| 키 | 의미 | 비고 |
| --- | --- | --- |
| `schema` | 설정 스키마 이름 | `version_id` 앞부분 |
| `interval_ms` | 이 간격마다 한 장을 목표로 한다 | 장면이 길수록 많이 뽑힌다 |
| `min_keyframes_per_scene` | 장면당 최소 장 수 | **하한이 2다.** FRD의 "복수 키프레임"이 근거이고 1을 허용하지 않는다 |
| `max_keyframes_per_scene` | 장면당 최대 장 수 | 후속 VLM·OCR의 비용 상한이기도 하다 |
| `edge_margin_ms` | 장면 경계에서 띄우는 여백 | 전환 잔상 회피. 구간이 짧으면 포기한다 |
| `candidates_per_slot` | 슬롯당 후보 수 | 1이면 선정이 사라지고 고정 간격 샘플링이 된다 |
| `candidate_step_ms` | 후보 간 간격 | |
| `score_stride` | 점수 계산 시 픽셀 건너뛰기 | 선명도의 상대 순위는 stride를 키워도 뒤집히지 않는다 |
| `min_luma_std` | 블랭크 판정 하한 | 암전·단색 전환·화이트아웃 |
| `jpeg_qscale` | mjpeg 품질(2~31, 낮을수록 고품질) | Pillow의 0~100과 다르다 |

**모든 수치가 실측 후 확정(FRD §11) 잠정값이다.** 근거가 생기면 파일을 v2로 복사하고 이 문서에
변경 근거를 남긴다.

### `min_keyframes_per_scene`은 슬롯 하한이지 출력 하한이 아니다

`plan_slots`는 `min(min_keyframes_per_scene, 창 안의 프레임 수)` 이상의 슬롯을 만든다 —
`_check_keyframe_count`의 기대치와 **같은 단위·같은 값**이다. 실제 장 수가 정해지는 곳은
선정이고, `select`가 슬롯을 버리는 경우가 둘인데 **둘의 뜻이 다르다.**

- **구간에 서로 다른 프레임이 그만큼 없다.** 후보가 이미 다른 슬롯이 고른 프레임으로 모인
  경우다. 그때 1장은 결함이 아니라 그 구간의 전부다. 여백을 빼면 그만큼의 프레임이 남지 않는
  창에서는 여백을 포기하므로, 이 갈래로 1장이 되는 경우는 **구간 전체에 프레임이 한 장뿐일
  때**뿐이다.
- **디코드가 후보 프레임에 닿지 못했다.** `measure`는 실제로 디코드한 프레임만 기록하므로
  scene 구간이 미디어 끝을 넘으면 뒤쪽 슬롯의 후보가 아예 없다. 이건 상류 scene이 이 미디어의
  것이 아니라는 신호다(길이가 다른 파일·잘린 입력).

#### 여백을 포기하는 기준이 ms가 아니라 프레임인 이유

처음에는 슬롯 상한이 창의 **ms 폭**이었고, 여백은 `duration <= 2 * edge_margin_ms`일 때만
포기했다. 그래서 `duration`이 `2 * edge_margin_ms`를 조금 넘으면 여백을 뺀 창이 몇 ms만
남는데, 그 안의 슬롯 중심과 후보가 전부 같은 프레임으로 반올림된다. `select` 규칙 3이 뒤
슬롯을 버려 1장이 되고, 검사는 2장을 요구해 **치명 단계가 영구 실패**했다. 기본 설정 실측
(fps 10종 × scene 시작 9종 × `duration` 1~1200ms = 106,590):

| fps | 실패하던 `duration` |
| --- | --- |
| 10 | 501~599ms |
| 23.976 / 24 / 25 | 501~540 / 501~530 / 501~537ms |
| 29.97 / 30 | 501~533 / 501~534ms |
| 50 / 59.94 / 60 | 501~519 / 501~513 / 501~513ms |
| 120 | 501~508ms |

상한이 `2 × edge_margin_ms + 한 프레임 간격`이라 **fps가 낮을수록 넓다.** ms 기준으로
막으려는 시도는 여기서 실패한다 — "창이 2ms 남았다"는 "두 장을 담는다"와 아무 관계가 없다.
그래서 두 곳을 프레임 수로 옮겼고, 같은 스윕에서 실패가 0이 됐다. 슬롯마다 남은 후보 중
무엇이든 최고 점수가 될 수 있다고 보는 탐색으로도 0이다(`select` 규칙 3은 그리디이므로 후보
집합이 겹치면 매칭이 존재해도 슬롯이 버려질 수 있다).

`edge_margin_ms`를 키우면 이 경계도 함께 커진다(500으로 올리면 1199ms까지). `duration`이
1000ms 이상인 장면의 슬롯 계획은 fps·시작 시각과 무관하게 이 변경 전과 동일하다.

**도달 경로.** `scene_detection`은 `min_scene_len_ms`보다 짧은 꼬리 scene을 직전 scene에
흡수시키지만 그 판단은 scene이 2개 이상일 때만 돈다. 컷이 하나도 없는 0.5초대 클립은
그대로 이 구간에 들어온다. 더 근본적으로 계약(`docs/contracts/job-api.md` §4.3.1)은 최소
scene 길이를 요구하지 않고 워커의 `_validate_scenes`도 검사하지 않는다 — 다른 단계의 설정
하나에 치명 단계의 성공이 걸려 있어서는 안 되므로, 이 단계가 창을 프레임으로 재서 스스로
보증한다.

그래서 `extract_keyframes`는 장면마다 `min(min_keyframes_per_scene, 구간의 프레임 수)`를
기대치로 두고 그보다 적으면 멈춘다(`_check_keyframe_count`). 앞쪽은 상한에 걸려 통과하고
뒤쪽만 실패한다. 0장만 막던 이전 판단에서는 **구간의 일부만 미디어에 있으면 한 장으로
succeeded가 됐다** — 같은 사실이 정도에 따라 실패와 성공으로 갈렸고, BE는 그 장면의 keyframe이
원래 그만큼인 줄 알게 된다. `ValueError`이므로 잡 레이어가 영구 `VALIDATION_ERROR`로 번역한다.
재시도가 고칠 수 없다 — BE는 같은 scene 목록을 다시 보낸다.

재현성 식별자는 `(config_version, engine, engine_version)` 튜플이다. `config_version`은 설정
파일만 해시하므로 디코더·인코더나 numpy가 바뀌면 값이 그대로인데 고른 프레임이나 저장된
바이트는 달라질 수 있다. 그래서 `engine_version`에 PyAV와 numpy 버전을 함께 적는다 — numpy가
바뀌면 같은 픽셀에서 점수가 미세하게 달라져 **다른 프레임이 대표로 뽑힐 수 있다.**

**워커 코드 변경도 같은 사각지대다.** 위의 여백 수정은 설정 파일을 건드리지 않으므로
`config_version`이 그대로인데 500ms대 장면의 선택 결과를 바꿨다. 값이 하나도 바뀌지 않은
파일을 v2로 복사해 두 저장소의 고정 벡터를 갈아엎는 비용이 얻는 것보다 크다고 보고 버전을
올리지 않았다. 재처리 결과를 비교할 때 세 필드가 같아도 워커 버전이 다르면 다를 수 있다는
뜻이므로 여기 적어 둔다.

고정 테스트 벡터는 계약 문서 §7에 있고 `tests/test_job_contract.py`가 대조한다. 값이 바뀌면
양쪽을 함께 고친다.

## 8. 재처리에서 중복이 생기지 않는 이유

네 겹이다. 앞의 세 겹은 계약 §8이 이미 정한 것이고, 워커의 몫은 마지막 하나다.

1. **fencing** — 회수된 lease로 오는 `complete`는 `JOB_409_002`. 좀비 워커가 두 번째 keyframe
   뭉치를 넣을 수 없다. 중단 지시를 받으면 워커는 **올리지도 않는다.**
2. **상태 전이 가드** — 이미 `succeeded`인 단계는 `JOB_409_001`.
3. **한 트랜잭션** — `scene`/`keyframe` INSERT와 `stage_states_json` 갱신이 하나의 트랜잭션이다.
4. **결정론** — 같은 입력과 같은 재현 튜플이면 같은 프레임을 고르고 같은 바이트를 쓴다. 샘플
   클립으로 두 번 돌려 파일 23개와 `keyframes.json`이 sha256까지 동일함을 확인했다(§9).

재시도(attempt N+1)는 새 `outputKeyPrefix`를 받으므로 실패한 attempt N의 JPEG이 성공 결과와
섞이지 않는다. 반대로 **같은 attempt를 다시 돌리면 같은 키에 같은 바이트를 쓴다** — 덮어써도
내용이 같으므로 산출물이 늘어나지 않는다.

## 9. 샘플 클립 실측

```bash
uv run --directory ai python -m npick_worker.frame_extraction.report \
    samples/KNI_02205.mp4 --out samples/out/KNI_02205-frames
```

`KNI_02205`(76초, 800x450, 30fps, scene 10개) 결과다.

| 항목 | 값 |
| --- | --- |
| keyframe | 23장 (장면당 2~5장) |
| 대표 이미지 | 장면마다 1장 |
| blank 판정 | 0장 |
| 총 용량 | 1,675 KiB (장당 평균 73 KiB) |
| 해상도 | 800x450 (원본 유지) |
| 경과 시간 | **총 19.4~19.6초** = scene 분할 14.8~15.0초 + keyframe 추출 4.6초 |
| 재실행 | 두 번 돌려 파일 23개와 `keyframes.json`이 sha256까지 동일 |

경과 시간은 `report` 명령이 출력한 값이고 두 번 실행의 범위다. 장비는 Intel 22코어 CPU·
GPU 미사용(이 단계는 CPU 디코드만 쓴다), Python 3.12.14, PyAV 18.1.0이다. FRD §8.2가
"장비·영상 조건 명시"를 요구하므로 함께 적는다.

**76초 클립에서 이 단계의 몫은 4.6초다.** FRD §8.2의 "짧은 영상 분석 30초"는 파이프라인
11단계 전체의 목표이므로, 디코드를 두 번 하는 판단(§6)이 그 목표를 위협하는지는 이 숫자로
판단한다 — 한 번으로 줄여도 아낄 수 있는 것이 최대 2초대다. 상류 scene 분할이 3배 더 걸리는
것이 먼저 볼 자리다.

가장 긴 scene 0(약 39초, 앵커 인트로)이 상한인 5장을 받았고 나머지 아홉은 하한인 2장을 받았다.
이 클립은 뒷부분 장면이 평균 4초 안팎이라 `interval_ms`(3초)가 상한·하한에 걸리지 않고 실제로
작동하는 구간이 scene 0 하나뿐이다 — 장면이 긴 클립(samples/README.md의 8번)이 들어오면 그때
간격을 다시 본다.

## 10. 언제 다시 볼 것인가

- **`interval_ms`·`max_keyframes_per_scene`** — 장면당 장 수가 곧 VLM·OCR 비용이다. 후속 단계의
  실측 처리 시간이 나오면 그 비용과 검색 품질을 함께 보고 정한다.
- **`jpeg_qscale`** — OCR 정확도와의 관계를 개발셋으로 측정한 뒤 확정한다. 지금 값은 "작은 글자에
  후하게"라는 방향만 반영한 잠정값이다.
- **선명도 기준** — 라플라시안 분산이 자막·슈퍼가 많은 프레임을 선호한다. 대표 이미지로는 그게
  맞지만, 검수자가 "장면을 대표하는 화면"으로 느끼는 것과 어긋날 수 있다. 사용자 평가에서
  확인할 항목이다.
- **디코드 1회로 줄이기** — 긴 클립의 처리 시간이 FRD §8.2 목표에 걸리면 §6의 대안을
  `FrameGrabber` 뒤에서 교체한다. 76초 클립에서 이 단계가 4.6초이므로(§9) 지금은 근거가
  없다 — 아껴도 2초대이고 후보를 원본 해상도로 쥐는 비용을 새로 진다.
- **scene 단위 write→upload** — 저장하는 keyframe의 디스크 상한이 장면 수에 비례한다(§6).
  긴 클립이나 장면이 많은 클립에서 파드 디스크가 문제가 되면 `FrameGrabber`와
  `StageOutcome.uploads`의 모양을 바꿔 장면 단위로 쓰고 올린다. 지금 구성(장면 100개 ≈
  200 MiB)에서는 근거가 없다.
