# OCR 선정과 설정

FRD `F-03` 화면 글자 읽기 구현 근거. 구현은 `src/npick_worker/ocr/`.

만들어야 하는 것은 FRD가 정한 넷이다 — **읽은 원문, 신뢰도, 위치, 해당 키프레임**
(`docs/frd.md:123`). 잡 API 쪽 규약(입력·출력 모양)은
[../../docs/contracts/job-api.md](../../docs/contracts/job-api.md) §4.3.2가 정본이고, 이
문서는 **왜 이렇게 읽는가**를 적는다.

## 1. 스키마가 정한 것과 정하지 않은 것

이 단계의 설계 여지도 대부분 테이블이 이미 좁혀 놓았다.

```sql
CREATE TABLE "ocr_observation" (
    "ocr_observation_id" bigint       NOT NULL,
    "keyframe_id"        bigint       NOT NULL,
    "raw_text"           text         NOT NULL,
    "tokens"             text         NOT NULL,
    "confidence"         numeric(5,4) NOT NULL,
    "bounding_box_json"  jsonb        NOT NULL,
    CONSTRAINT ck_ocr_confidence CHECK (confidence BETWEEN 0 AND 1)
);
```

| 요구 | 스키마의 자리 | 결과 |
| --- | --- | --- |
| 해당 keyframe | `keyframe_id` | 워커는 `(sceneIndex, timestampMs)`로 보내고 BE가 행을 찾는다 (§7) |
| OCR 원문 | `raw_text` | 엔진이 읽은 그대로. 컬럼 주석이 "절대 덮어쓰지 않는다" |
| 검색 토큰 | `tokens` | Kiwi 형태소. **색인과 질의가 같은 설정**이어야 한다 (§6) |
| 신뢰도 | `confidence` | `numeric(5,4)` — 넷째 자리까지다 |
| 위치 | `bounding_box_json` | 원본 해상도 픽셀 좌표. 사변형을 그대로 담는다 |
| 검증 상태 | **없음** | 컬럼 주석: "이 값의 임계값으로 검증 상태를 판정한다" (§5) |
| 병합 그룹 | **없음** | 그래서 병합을 저장하지 않는다 (§4) |

## 2. 엔진 선정 — 실측

한국어 OCR 후보 다섯을 **같은 입력**에 돌렸다. 입력은 `frame_extraction`이 샘플 클립
`KNI_02205`에서 뽑은 keyframe 23장(800x450)이고, 정답은 그 23장을 사람이 직접 보고 적은
`samples/ocr-ground-truth.KNI_02205.json`이다. 읽을 수 있는 문구 37개가 분모다.

측정 장비는 Intel 22코어 CPU, GPU 미사용(§9와 같다).

| 후보 | 재현율 | 장당 | 명백한 오탐 | 설치 | 패키지 | 실행기 |
| --- | --- | --- | --- | --- | --- | --- |
| PaddleOCR (server det) | **31/37** | 12,016 ms | 0 | 807 MB | 72 | paddlepaddle |
| PaddleOCR (mobile det) | 28/37 | 1,124 ms | 4 | 807 MB | 72 | paddlepaddle |
| **RapidOCR korean (선택 설정)** | **27/37** | **~430 ms** | 1 | 276 MB | 22 | onnxruntime |
| RapidOCR korean (server det) | 26/37 | 2,205 ms | 0 | 276 MB | 22 | onnxruntime |
| EasyOCR `ko`+`en` | 16/37 | 1,240 ms | 0 | 910 MB | 26 | torch |
| RapidOCR 1.4.4 기본 (`ch`/`en`) | 13/37 | 2,505 ms | 0 | — | — | onnxruntime |

- **"명백한 오탐"** 은 화면에 글자가 아예 없는 프레임(23장 중 4장)에서 나온 출력이다.
  글자가 있는데 잘못 읽은 것은 사람도 못 읽는 작은 글자와 구분할 수 없어 따로 센다.
- **"설치"** 는 빈 venv에 그 후보만 넣었을 때의 크기다. 모델 가중치는 별도로
  PaddleOCR 103 MB, RapidOCR 19 MB(검출 4.8 + 인식 13.5 + 방향 0.6), EasyOCR 95 MB다.
- 마지막 줄은 **한국어 모델이 없는** 기본 설정이다. "RapidOCR은 한국어를 못 읽는다"가
  아니라 "기본값이 중국어·영어다"라는 것을 남겨 둔다.

### 왜 RapidOCR인가

**인식 모델이 PaddleOCR과 같은 것이다.** 둘 다 `korean_PP-OCRv5_rec_mobile`을 쓰고,
RapidOCR은 그 ONNX 판을 onnxruntime으로 돌린다. 남는 차이는 검출 전처리이고 그건 우리
설정 파일의 축이다 — 실제로 검출 파라미터만 바꿔 22/37에서 27/37까지 움직였다.

그래서 선택 기준은 정확도가 아니라 비용이 됐다.

| | PaddleOCR | RapidOCR |
| --- | --- | --- |
| 재현율(이 표본) | 28/37 | 27/37 |
| 이미지 증가 | +807 MB / 72 패키지 | +276 MB / 22 패키지 |
| CPU 실행 | Windows에서 `enable_mkldnn=False` 필수 | 그대로 동작 |
| GPU 전환 | paddlepaddle-gpu (별도 휠) | onnxruntime-gpu (같은 API) |

`infra/compose/profiles/pipeline.yml`이 "CPU 워커와 GPU 파드가 같은 이미지를 쓴다"로
적었으므로 그 807 MB는 OCR을 돌리지 않는 워커에도 실린다.

**Windows CPU의 paddlepaddle 3.3.1은 실제로 죽었다.** oneDNN 경로에서
`NotImplementedError: ConvertPirAttribute2RuntimeAttribute`가 나 `enable_mkldnn=False`로
우회해야 했고, 그 우회가 위 표의 12초짜리 측정을 만들었다. 팀 개발 환경이 Windows다.

**1/37 차이는 이 표본에서 결정적이지 않다.** 클립 한 편·800x450·문구 37개다. 그래서
엔진은 `OcrEngine` Protocol 뒤에 두었다(`ocr/engine.py`). 1080p 클립으로 다시 재서
PaddleOCR이 유의미하게 앞서면 바뀌는 것은 backend 파일 하나와 설정이다.

### 후보에서 뺀 것

- **외부 OCR API**(Naver CLOVA, Google Vision) — FRD §6.4가 미확인 자료의 외부 전송을
  금지하고 §13.4가 외부 전송을 별도 승인 대상으로 둔다. 승인 절차 없이 기본 경로로
  삼을 수 없다.
- **Tesseract** — 한국어 방송 화면(굵은 고딕·색 배경·기울어진 현판)에서 위 후보들과
  비교 대상이 되지 못하고, 시스템 바이너리 의존이 추가된다.
- **VLM에게 읽히기** — OCR 단계와 VLM 단계가 같은 일을 두 번 하게 되고,
  글줄 단위 `bounding_box_json`을 얻을 수 없다.

## 3. 무엇을 관측으로 남기는가

**글줄 하나가 행 하나다.** 문단으로 합치지 않는다 — 합치면 `bounding_box_json`이 여러
줄을 덮는 사각형이 되어 "어디서 읽었는지"를 가리키지 못하고, confidence도 하나로 뭉개져
줄마다 다른 품질이 사라진다.

**빈 원문은 버린다.** 검출기가 상자를 잡았는데 인식이 아무 글자도 내지 못하는 경우가
있다(측정에서 PaddleOCR이 `''`를 여러 건 냈다). `raw_text`가 `NOT NULL`이고, 빈 행은
검색에도 근거 표시에도 쓸 수 없다.

**`raw_text`는 손대지 않는다.** 정규화(NFKC·소문자)는 `tokens`를 만들 때만 적용한다.
컬럼 주석이 "읽은 그대로. 결과 화면에 근거로 보여준다. 절대 덮어쓰지 않는다"이다.
**앞뒤 공백도 떼지 않는다** — `strip()`은 빈 원문을 가려내는 판정에만 쓰고 저장할 값에는
쓰지 않는다. 공백 하나라도 고치면 "엔진이 읽은 그대로"가 아니게 된다.

**confidence는 넷째 자리에서 반올림해 보낸다.** `numeric(5,4)`라 다섯째 자리를 보내면
DB가 반올림하고, 그러면 워커 로그의 값과 저장된 값이 갈린다.

**상자는 사변형 그대로다.** 검출기가 주는 것이 축에 나란한 사각형이 아니다. 축에 맞춰
펴면 기울어진 현판·배너에서 실제보다 넓은 영역을 가리키는데, 이 값의 용도가 근거 이미지
위에 상자를 그리는 것(컬럼 주석)이라 그 어긋남이 그대로 보인다. `x`·`y`·`width`·`height`는
사변형에서 유도해 함께 담아, 사변형을 쓰지 않는 소비자가 다시 계산하지 않게 한다.

## 4. Frame 간 병합과 원본 보존 (S15P21A501-95)

`merge.py`는 같은 scene의 관측을 문구 그룹으로 묶는다. 원본 배열을 줄이거나 덮어쓰지
않고 `textGroups`가 그 배열의 0-based 인덱스를 참조한다. 단독 관측도 그룹 하나다.
대표는 confidence가 가장 높은 원본 관측이며, 동률은 시각·파일·bbox·원문 순서로 정한다.
대표의 confidence는 그 관측의 값일 뿐 그룹 전체의 정확도가 아니다. 구성원 각각의
미검증 상태를 유지하며 `verified`를 새로 만들지 않는다.

비교값은 원문에 NFKC·casefold·공백 제거를 적용한 문자열이다. 원문과 검색 토큰은
바꾸지 않는다. 기존 `text_key`는 검색 토큰 해시이므로 다른 원문도 같은 키를 가질 수
있다. 이를 병합의 충분조건으로 쓰면 숫자나 짧은 표현의 차이를 잃을 수 있어, 병합은
원문 비교값으로 판정한다. 기존 키는 검색용 호환성을 위해 그대로 제공한다.

기본 `similarity_threshold=1.0`은 비교값 일치만 허용한다. 낮추면 양방향
`SequenceMatcher(autojunk=False)` 중 낮은 유사도로 비교한다. 숫자열 또는 구두점·기호가
다르면 유사도와 무관하게 병합하지 않는다. 그룹의 **모든 구성원**과 호환돼야 들어갈 수
있어 A–B, B–C만 유사한 연쇄 병합을 막는다. 의미 동등성을 판정하는 모델은 아니다.

같은 frame의 동일·유사 문구는 별개 관측으로 둔다. 한 frame에 대응 가능한 관측이 둘
이상이면 어느 bbox의 문구가 반복된 것인지 불명확하므로 그 관측들은 병합에서 제외한다.
여러 그룹에 동시에 들어갈 수 있는 관측도 별개로 남긴다. bbox 거리나 시간 간격 임계값은
아직 도입하지 않았다. 따라서 같은 scene에서 사라졌다 재등장한 문구를 묶을 수 있고,
그룹을 연속 노출 시간 구간으로 해석해서는 안 된다.

출력 계약은 `npick.stage.ocr.output/v2`다. 워커는 `observations`·`textGroups`·설정 버전을
출력에 담고, 같은 내용을 `ocr_result` 종류의 `ocr-result.json` 파일로도 올린다.
파일에는 출력 스키마와 재현 튜플까지 포함한다. 참조 배열을 단독 정렬·필터링하지 않는다.
그룹별 대표를 읽어 문구 하나씩 소비하고, 근거가 필요하면 구성원 인덱스로 원본을 찾는다.
BE의 OCR 저장·배정 및 이 산출물의 후속 소비 연결은 아직 미구현이다. 이 변경이 DB
저장이나 실제 검색 연동 완료를 뜻하지 않는다.

실측 재현 명령:

```bash
uv run --directory ai python samples/evaluate_ocr_merge.py
uv run --directory ai python -m npick_worker.ocr.report samples/out/KNI_02205-frames --out samples/out/ocr-merge-95-live
```

첫 명령은 로컬 `samples/out/KNI_02205-ocr/ocr.json`의 실제 OCR 관측 44건과
SHA256으로 묶인 임시 라벨을 사용한다. OCR 원문 출력은 커밋하지 않으며 기존 OCR
report 명령으로 재생성한다. `--input`으로 다른 report 경로를 지정할 수 있다.
개발 비교는 scene 0, 분리 검증은 scene 8·9의 관측 쌍이다. 라벨은 기존 사람이 적은
프레임 전사와 OCR 원문을 참고한 **AI 예비 라벨**이며 독립 검수 Gold Set이 아니다.
평가 JSON 및 임계값별 전체 출력은 `samples/out/ocr-merge-95/`에 쓴다.

| 유사도 임계값 | 그룹 수 | 개발 정답 병합 / 3쌍 | 분리 검증 정답 병합 / 3쌍 | 라벨된 음성 쌍 오병합 / 10쌍 |
| --- | --- | --- | --- | --- |
| 1.0 (기본) | 40 | 1 | 3 | 0 |
| 0.95 / 0.90 | 40 | 1 | 3 | 0 |
| 0.85 | 39 | 2 | 3 | 0 |
| 0.80 | 40 | 3 | 1 | 0 |

0.80에서는 개발 문구 두 쌍을 더 잡지만 scene 8의 서로 다른 문구가 유사 후보가 되어
모호성 보호가 병합을 보류한다. 0.85의 일반화 근거도 한 클립으로는 부족하다. 따라서
기본값은 1.0으로 유지한다. 오병합 0은 라벨된 10개 음성 쌍에서의 결과이며 전체 데이터
정확도 주장이 아니다. 모든 설정에서 원본 44건 보존, 참조 검증, JSON 왕복 및 결정론적
재실행을 확인했다. 병합·출력 검증은 이 표본에서 약 1~3ms였다.

2026-09-14 실제 엔진 재실행은 800x450 keyframe 23장, 원본 관측 44건, 미검증 12건,
병합 그룹 40개, 경과 28.9초였다(Windows CPU, 모델 생성 포함). 뉴스 하단 자막바를
포함한 다중 클립 검증 및 실제 BE 연동은 남아 있다. report의 그룹 인덱스는
`keyframes[].observations[]`를 순서대로 평탄화한 배열을 가리킨다.

검증: OCR·병합·잡 계약·레지스트리·러너·클라이언트·미디어 회귀 260건 통과 후,
추가한 기본 버전 벡터와 실제 핸들러의 JSON 업로드 테스트까지 포함한 집중 검사 23건도
통과했다(중복 제외 262건, 실제 모델 smoke 표식 2건은 해당 pytest 실행에서 제외).
실제 엔진 검증은 위 CLI로 별도 수행했으며 재실행 원본 관측이 기존 44건과 전부 같았다.
Ruff와 변경 관련 mypy 검사도 통과했다. 가짜 BE를 사용한 업로드 테스트는 실제 BE
저장·조회 통합 증거로 보지 않는다.

## 5. 임계값은 실측으로 정했다

티켓 제약이 "OCR confidence 품질 기준값은 임의의 고정값으로 정하지 않고 개발 중 실제
데이터로 측정해 확정"이다. FRD §11의 "실행 환경 설정값은 개발하면서 실측으로 정함"과
같은 요구다.

샘플 keyframe 23장에서 나온 관측 44건(정답 27건, 오독 17건)을 ground truth와 대조해
임계값을 훑었다.

| 임계값 | 검증됨 | 그중 정답 | unverified | 그중 오독 | 잃은 정답 |
| --- | --- | --- | --- | --- | --- |
| 0.60 | 34 | 27 | 10 | 10 | 0 |
| 0.65 | 34 | 27 | 10 | 10 | 0 |
| **0.70** | **32** | **27** | **12** | **12** | **0** |
| 0.75 | 32 | 27 | 12 | 12 | 0 |
| 0.80 | 28 | 24 | 16 | 13 | 3 |
| 0.90 | 24 | 21 | 20 | 14 | 6 |

**0.80이 무너지는 자리다.** 거기서 처음으로 맞게 읽은 것이 `unverified`로 떨어지고, 그
대가로 걸러지는 오독은 12건에서 13건으로 하나 늘 뿐이다. 0.70과 0.75는 이 표본에서
결과가 같아 낮은 쪽을 골랐다.

`min_confidence = 0.70`에서 `unverified`로 표시되는 12건은 **전부 오독**이다.

### 미달이라고 버리지 않는다

`unverified`는 **표시**이지 필터가 아니다. 티켓 제약이 "검색 후보에는 사용할 수 있으나
검증된 사실이나 hard conflict 근거로 사용하지 않음"이므로 관측은 전부 저장한다.

그래서 rapidocr의 `Global.text_score`를 0으로 고정하고 **설정 키로 열지 않았다.** 그 값의
기본이 0.5라 그 아래를 말없이 버리는데, toml 한 줄로 관측이 사라지는 길을 남겨 두면
"원문을 절대 덮어쓰지 않는다"가 설정 실수 하나로 깨진다.

**높은 confidence만으로 `verified`가 되지도 않는다.** FRD `docs/frd.md:151`이 "AI의 높은
신뢰도만으로 검증된 사실로 올리지 않는다"이고, 검증 상태를 담는 곳은
`tag_evidence.verification_status`이지 이 단계가 아니다. 이 단계가 하는 일은 임계값과
그때 쓴 값을 결과에 함께 실어 나중에 재현할 수 있게 하는 것까지다.

## 6. 토큰은 질의 쪽과 같은 규칙이어야 한다

`ocr_observation.tokens`는 이 단계의 산출물이다. BE에는 Kiwi가 없고
`docs/architecture/02-container.md:110`이 "워커가 Kiwi로 토큰화한 결과를 별도 컬럼에 넣고
`pdb.whitespace` 토크나이저로 색인한다"로 정했다. 같은 문장이 **색인과 질의가 동일한
Kiwi 설정을 써야 하며 다르면 검색이 0건이 된다**고 못 박는다.

그래서 규칙을 `npick_worker/korean_tokens.py` 하나로 옮기고 양쪽이 그것을 쓴다.

- 질의 쪽 `query_normalization.normalize()`의 `search_tokens`
- 문서 쪽 `ocr` 단계의 `tokens`

`timecode.py`를 `scene_detection`과 `frame_extraction`이 나눠 쓰는 것과 같은 구조다.
설정 파일도 하나여야 하므로 `korean_tokens`가 `query_normalization`의 설정을 읽는다 —
`keep_pos` 하나만 어긋나도 토큰 경계가 달라진다. `ai/AGENTS.md`가 "리졸버와 워커가
공유하는 것은 `versioning.py` 뿐"으로 적어 두었던 경계는 이 요구 때문에 한 칸 넓어졌고,
그 문서도 함께 고쳤다.

**별칭·불용어·정렬은 공유하지 않는다.** 그것들은 질의 지문(`normalized_query`) 전용이고,
색인 측이 하지 않는 변형을 질의에만 걸면 매칭이 어긋난다.

`tests/test_ocr.py`의 `test_tokens_use_the_same_rule_as_the_query_side`가 이 한 문장을
지킨다.

## 7. keyframe을 어떻게 가리키는가

`ocr_observation.keyframe_id`는 TSID이고 그것을 발급하는 쪽은 BE다. `complete` 응답의
`assignedIds`는 scene만 돌려준다(계약 §4.3). 그래서 워커는 **`(sceneIndex, timestampMs)`**
로 말하고 BE가 `keyframe`의 `UNIQUE(scene_id, timestamp_ms)`로 행을 찾는다.

셋 중 하나를 골라야 했다.

| 안 | 판단 |
| --- | --- |
| `(sceneIndex, timestampMs)` (선택) | 스키마도 `assignedIds`도 안 바꾼다. UNIQUE 제약이 이미 이 쌍을 행 하나로 보증한다 |
| `assignedIds.keyframes` 추가 | 계약과 BE 구현을 함께 고쳐야 한다. 얻는 것은 조회 한 번 |
| `storageKey`로 참조 | BE가 `keyframe.storage_key`로 역조회해야 하는데 그 컬럼에 인덱스가 없다 |

`storageKey`는 **근거로 함께 싣는다** — 어느 파일을 읽었는지가 남아야 나중에 조사할 수
있다. 참조 키는 아니다.

## 8. 원본 해상도와 검출 축소

FRD는 "작은 글자를 읽을 때는 축소된 대표 이미지 대신 원본 해상도의 프레임을 사용한다"
(`docs/frd.md:131`)를 요구한다. 이 단계는 **`frame_extraction`이 원본 해상도로 저장한
JPEG을 그대로 읽는다.** 영상에서 프레임을 다시 뽑지 않는다 — 다시 뽑으면 `keyframe` 행이
가리키는 이미지와 읽은 이미지가 달라질 수 있다.

**다만 검출기에는 축소본이 들어간다.** PP-OCR 구조가 그렇다.

1. 검출기가 `det_limit_side_len`에 맞춰 줄인 이미지에서 글자 상자를 찾는다.
2. 찾은 상자를 **원본 좌표로 되돌린다.**
3. 인식기는 **원본 이미지에서 잘라낸 조각**을 읽는다.

그래서 FRD가 요구하는 "원본 해상도로 읽기"는 3번에서 지켜진다. 축소가 영향을 주는 것은
"작은 글자를 **찾아내는가**"뿐이다.

기본값 960은 샘플(800x450)에서 아무 일도 하지 않는다 — 긴 변이 이미 960 미만이라 축소가
일어나지 않는다. **그래서 이 값은 아직 실측으로 확정된 것이 아니다.** 1080p가 들어오면
실제 축소가 걸리므로 그때 다시 잰다(§10).

### 축이 하나 더 있었다 — 전체 이미지 전처리

위 3단계는 rapidocr의 기본 설정에서 **참이 아니었다.** 검출기 리사이즈 앞에 전처리가
하나 더 돌고(`rapidocr/main.py`의 `preprocess_img`), 그것이 `Global.max_side_len=2000`으로
**이미지 자체를 줄인 뒤 그 줄인 이미지에서 인식 조각을 잘라낸다**(`detect_and_crop` →
`crop_text_regions`). 상자 좌표는 원본으로 복원되지만 인식에 들어간 픽셀은 돌아오지 않는다.

| 입력 | 전처리 후 |
| --- | --- |
| 3840x2160 | 1984x1120 |
| 2560x1440 | 1984x1120 |
| 1920x1080 | 그대로 |

`Global.use_preprocess_img = False`로 껐다. FRD의 요구에는 해상도 조건이 없으므로
1440p 이상에서만 깨지는 것도 깨지는 것이다. 이 값은 `det_limit_side_len`과 달리 **설정
키가 아니다** — `text_score`와 같은 이유로, toml 한 줄로 FRD 요구가 무너지는 길을 두지
않는다(§5의 같은 판단).

이 결함은 코드 리뷰에서 나왔고 샘플이 800x450이라 이 문서의 수치에는 영향이 없다. 고친
뒤 다시 돌려 `ocr.json`이 **sha256까지 같았다.**

## 9. 샘플 클립 실측

```bash
uv run --directory ai python -m npick_worker.ocr.report \
    samples/out/KNI_02205-frames --out samples/out/KNI_02205-ocr
```

`KNI_02205`(76초, 800x450, scene 10개, keyframe 23장) 결과다.

| 항목 | 값 |
| --- | --- |
| 관측 | 44건 (글자가 있던 프레임 14장) |
| 문구 (94번 당시 전역 text_key 집계) | 35종. 95번의 scene별 보수적 그룹 수 40개와 다른 지표 (§4) |
| `unverified` | 12건 (임계값 0.70) |
| legible 재현율 | 27/37 |
| 경과 시간 | **9.8~10.0초** (장당 427~433 ms, 엔진 생성 포함) |
| 재실행 | 두 번 돌려 `ocr.json`이 sha256까지 동일 |

장비는 Intel 22코어 CPU·GPU 미사용, Python 3.12.14, rapidocr 3.9.2 + onnxruntime 1.29.0.
FRD §8.2가 "장비·영상 조건 명시"를 요구하므로 함께 적는다. **한산한 장비 기준이다** —
onnxruntime이 22스레드를 다 쓰므로 다른 작업이 도는 동안 재면 같은 입력이 4~5배까지
느려진다(재측정 시 47~52초). 이 표의 값과 비교할 때는 부하 조건을 맞춰야 한다.

이 경과 시간은 **CLI를 한 번 돌린 값이라 엔진 생성이 한 번 들어 있다.** 워커에서는
엔진이 프로세스에 하나뿐이므로(`rapidocr_backend.shared_engine`) 생성 비용은 기동 때
워밍업에서 한 번만 들고, 잡이 실제로 내는 것은 프레임 처리 시간이다.

읽어 낸 것의 예(현판이 큰 프레임):

```
    8      71833  5   강원도(1.00) | 대표 볼거리관(1.00) | 강원도 대표(0.94) |
                      볼거리관(0.99) | 강원도(1.00)
    9      73833  7   우수상품관(1.00) | 우수상품관(1.00) | Best Probuct pavliet(0.79) |
                      !fee Paidt palie(0.55) | Life Style(0.92) | !IfeStle(0.45) | Beauty Sty(0.98)
```

`!`가 `unverified`다. 오독이 낮은 confidence에 몰리는 것이 §5 표의 근거다.

**76초 클립에서 이 단계의 몫은 약 10초다.** 상류 두 단계가 19.4~19.6초이므로
(`frame-extraction.md` §9) 세 단계 합이 30초 안팎이다. FRD §8.2의 "짧은 영상 분석 30초"는
파이프라인 10단계 전체의 목표이므로 **이 조합으로는 이미 빠듯하다.** 남은 일곱 단계가
붙기 전에 볼 자리는 scene 분할(14.8~15.0초)이 먼저다.

### 결정론

같은 입력·같은 설정으로 두 번 돌려 `ocr.json`이 sha256까지 같았다. 계약 §8의 재처리
중복 방지 중 워커의 몫이 이것이다.

**다만 장비 사이의 동일성은 보장하지 않는다.** onnxruntime의 스레드 수가 기본값(코어 수)
이라 부동소수 누적 순서가 장비마다 달라질 수 있다. 같은 장비에서의 재실행이 같다는 것과
개발 머신과 GPU 파드의 결과가 비트 단위로 같다는 것은 다른 주장이고, 여기서 확인한 것은
앞엣것뿐이다.

## 10. 설정과 버전

정본: `src/npick_worker/config/ocr.v1.toml`. **임계값을 코드에 두지 않는다.**

| 키 | 의미 | 비고 |
| --- | --- | --- |
| `schema` | 설정 스키마 이름 | `version_id` 앞부분 |
| `ocr_version` | 모델 세대 | `PP-OCRv5` |
| `det_lang` / `det_model_type` | 검출 모델 | PP-OCRv5 검출기는 `ch` 하나가 다국어 공용이다 |
| `rec_lang` / `rec_model_type` | 인식 모델 | `korean` — paddleocr `lang="korean"` 과 같은 가중치 |
| `det_limit_type` / `det_limit_side_len` | 검출 입력 크기 | 인식은 원본에서 자른다 (§8) |
| `det_thresh` | 확률 맵 이진화 문턱 | |
| `det_box_thresh` | 상자 평균 점수 하한 | 0.3으로 낮추면 재현율 23→25, 오탐 1→10 |
| `det_unclip_ratio` | 상자를 부풀리는 배율 | 글자가 경계에서 잘리는 것을 막는다 |
| `det_use_dilation` | 확률 맵 팽창 | 켜면 이웃한 별개 문구가 한 상자로 붙었다 |
| `min_confidence` | `unverified` 판정 하한 | **버리는 기준이 아니다** (§5) |

**설정 키가 아닌 것 둘.** `Global.text_score`(§5)와 `Global.use_preprocess_img`(§8)는
코드에 상수로 박아 두었다. 품질을 조절하는 값이 아니라 **깨지면 안 되는 요구**이기
때문이다 — 앞엣것은 "미달 관측도 남긴다", 뒤엣것은 "원본 해상도로 읽는다"이고, 둘 다
toml 한 줄로 조용히 무너질 수 있는 자리에 두면 안 된다.

모델 가중치의 위치는 이 파일이 아니라 환경 변수 `NPICK_AI_OCR_MODEL_DIR`이다. 품질을
바꾸는 값이 아니라 경로이기 때문이다. 컨테이너에서는 반드시 준다 — 기본값이
site-packages 안이라 컨테이너를 다시 만들 때마다 모델을 새로 받는다.

재현성 식별자는 `(config_version, engine, engine_version, tokenizer, merge_config_version)`
튜플이다. 병합 설정은 `src/npick_worker/config/ocr-merge.v1.toml`에 따로 두며 변경하면
`stageVersion`도 바뀐다. OCR 엔진 설정 해시는 그대로 유지한다. 실험할 때는 report의
`--merge-config <파일>` 옵션이나 `read_keyframes(..., merge_config=...)`를 사용한다.
워커 기본값 변경은 동봉 병합 설정을 수정하고 배포해야 하며 job의 임의 config로 덮지 않는다.

## 11. 언제 다시 볼 것인가

- **1080p 클립으로 전부 다시 잰다.** 이 문서의 수치는 800x450 한 편에서 나왔다. 셋이
  함께 움직인다 — `det_limit_side_len`(960이 그때는 실제 축소가 된다), `min_confidence`
  (해상도가 오르면 오독의 confidence 분포가 바뀐다), 그리고 엔진 선정 자체(§2의 1/37
  차이). `samples/README.md`의 1번 클립이 들어오면 그때다.
- ~~**뉴스 하단 자막바(슈퍼)를 아직 못 봤다.**~~ **봤다 — 긴 문장은 맞고, 따옴표 친
  짧은 강조어는 틀린다**(§12). 시연용 클립 15편(`samples/sample_0921`)의 긴 인터뷰
  자막 두 줄은 그 클립의 자막 파일과 글자 단위로 일치했다. 그런데 **이 티켓의 원
  사례 자체가 자막바였다** — `7년간 1,387억 '꿀꺽'` 의 따옴표 안 두 글자가 틀렸다
  (§12 의 화면 증거). 자막바를 한 덩어리로 "쓸 만하다" 고 말할 수 없다는 뜻이다.
  **사람이 적은 라벨은 아직 없다** — 위 확인은 자막 파일과의 대조이고, 화면에만 있는
  문구(이름표·출처·강조어)는 그 방법으로 못 잰다. 자막바가 포함된 클립의 ground
  truth 를 만들면 그때 §12 의 표에 줄이 는다.
- **`jpeg_qscale`과의 관계.** `frame-extraction.md` §10이 "OCR 정확도와 qscale의 관계를
  개발셋으로 측정한 뒤 확정한다"로 남겨 둔 항목이다. 이제 재는 도구가 생겼다 —
  `frame_extraction.report`를 qscale별로 돌리고 이 단계의 재현율을 비교하면 된다.
  **§12 의 정확일치로 재는 편이 낫다** — qscale이 깎는 것은 획의 경계이고, 그 손상은
  문구를 놓치는 쪽보다 글자가 바뀌는 쪽으로 먼저 나타난다. `eval/ocr/ocr_bench.py` 의
  `--frames` 에 qscale별 디렉터리를 주면 된다.
- **GPU.** 지금은 CPU다. `onnxruntime-gpu`로 바꾸면 같은 API로 돌아가지만, 이 단계가
  76초 클립에서 10초이므로 아직 근거가 없다. 파이프라인 전체가 §8.2 목표에 걸릴 때 본다.
- **장비 사이의 결정론.** §9의 한계다. 필요해지면 onnxruntime 스레드 수를 고정한다
  (`frame_extraction`이 mjpeg 인코더 스레드를 1로 고정한 것과 같은 처방).
- **검출 입력 크기를 올릴 것인가.** §12가 후보(`min`/1280 + `det_box_thresh` 0.8)와
  근거를 남겼다. **전환 조건은 셋이다** — 1080p 표본에서 같은 이득이 나는 것, 그때의
  2.3배 처리 시간을 파이프라인 전체 예산이 받아 주는 것(§8.2), 그리고 **표본 밖 클립을
  나쁘게 만들지 않는 것**. 셋째는 지금 성립하지 않는다(§12: 이 설정이 `sample_0921`
  15번 클립의 간판 세 문구를 전부 놓친다). 재는 도구는 `eval/ocr/` 이다.
  **후보를 다시 고를 때 볼 것** — 검색 도달은 올라도 색인 오염 토큰은 33 그대로다.
  오염까지 보면 `det-min-1152-box-0.8`(도달 28/37, 오염 28, 오탐 0)이 더 낫다(§12).
- **`꿀꺽` 은 OCR 로 닿지 않는다.** 색인 토큰이 비어 있어 정확히 읽어도 그 문구로는
  검색되지 않고, 질의도 `query_normalization` 이 거부한다(§12). **이 단계가 아니라
  토크나이저 쪽 문제다.** 같은 성질의 문구(의성어·의태어·짧은 강조어)가 화면에
  얼마나 있는지 세어 본 적이 없다 — 그 수가 나와야 고칠 값어치를 판단할 수 있다.
- **짧고 대조할 이웃이 없는 글자.** §12 가 좁혀 놓은 이 단계의 실제 약점이고, 설정으로
  닿지 않는다. 표본 안에서는 현장 간판·전시물의 작은 글자로, 원 사례에서는 자막바
  안의 두 글자짜리 강조어로 나타났다. 다음에 볼 곳은 인식 모델 쪽이다 — 한국어 server 인식 모델의 존재 여부,
  파인튜닝, 그리고 이 세 사례(`eval/ocr/cases.json`)를 판정 기준으로 쓰는 것.

## 12. 화면 글자를 잘못 읽는다 (S15P21A501-260)

QA 가 화면의 `꿀꺽` 을 `꿀찍` 으로 읽은 사례를 보고했다. 검출도 인식도 성공했고 **글자만
틀렸다.**

> **처음에는 `꿀떡` 으로 전달됐다.** 뒤늦게 화면 캡처가 들어와 원문이 `꿀꺽` 임이
> 확인됐다(캡처는 방송 화면이라 커밋하지 않는다 — 아래 「원 사례의 화면 증거」). 이
> 문서의 초판이 저장소를 `꿀떡` 으로 뒤져 원본을 찾지 못한 이유가 이것이다. 아래는
> 전부 `꿀꺽` 기준으로 고쳤고, 증거가 바꾼 두 가지 결론은 「원 사례의 화면 증거」에
> 따로 적었다.

### 이 실패는 §2·§5 의 표에 잡히지 않는다

그 표의 "재현율 27/37" 은 사람이 출력을 보고 "이건 읽어 낸 것" 으로 센 수치다. 그
세는 방식에서 `올림픽 G-1년 페스티벌` → `-립픽G-1년페스티벌` 은 정답 쪽에 들어간다.
사람 눈에는 읽어 낸 것이 맞다.

**같은 출력에서 글자까지 맞은 것은 16건뿐이다.** 27 과의 차이 11건 이상이 "읽어 냈지만
글자가 다른" 것이고, 재현율은 그것을 정답으로 센다.

**검색에는 아니다.** 티켓의 제약 "검색 근거로 OCR 토큰이 쓰이므로 품질이 검색에
영향" 이 가리키는 자리가 이것이다.

그래서 지표를 하나 더 두었다 — **정확일치**. 하네스는 `eval/ocr/` 이고 비교 규칙은
`merge.comparison_text` 를 그대로 쓴다. 정의와 한계는 [../eval/ocr/README.md](../eval/ocr/README.md) 다.

**다만 정확일치는 검색 성공률이 아니다.** 이 절의 초판이 그렇게 읽었고 틀렸다 —
검색이 맞대는 것은 원문이 아니라 토큰이다. 아래 「정확일치를 검색률로 읽으면 틀린다」
가 그 정정이고, 검색 쪽 수치는 거기서부터 읽는 것이 맞다.

### 기본 설정의 실제 상태

같은 표본(`KNI_02205`, keyframe 23장, legible 문구 37개)을 그 지표로 다시 재면:

| | 값 | |
| --- | --- | --- |
| 정확일치 | **16/37** | 재현율 27/37 과 같은 표본·같은 출력이다 |
| **검색 도달** | **21/37** | 라벨 토큰과 겹치는 관측이 있는 문구 |
| 못 찾음 | 16 | 토큰이 하나도 겹치지 않는다 |
| 오독 | 13 | |
| 누락 | 8 | |
| **색인 오염 토큰** | **33** | 화면에 근거가 없는데 색인에 들어가는 토큰 |
| 검증 표시 없는 오독 | 12 | confidence 분포를 보는 값이다. 색인 여부와 무관하다 |
| 명백한 오탐 | 1 | |

**정확일치와 검색 도달이 5건 어긋난다.** 글자가 틀렸는데도 토큰이 겹쳐 검색은 닿는
경우다(`지폐를 넣고` → `지패를 넣고` 에서 `넣`). 반대 방향도 있다 — 정확히 읽어도
토큰이 비면 못 찾는다. 두 수를 하나로 합쳐 읽으면 안 되는 이유가 이것이고, 자세한
것은 바로 아래 두 절이다.

이 표에서 이 티켓이 줄여야 하는 수는 **못 찾음 16** 과 **오염 토큰 33** 이다. §5 의
표가 "걸러낸 것" 을 셌다면 이 표는 **걸러지지 않고 색인에 들어간 것**을 센다.

### 정확일치를 검색률로 읽으면 틀린다

코드 리뷰가 짚었고, 확인해 보니 맞았다. **검색은 원문이 아니라 토큰을 맞댄다.**

색인 쪽 `ocr_observation.tokens` 는 `korean_tokens.index_tokens` 가 만들고
(`ocr/postprocess.py`), 질의 쪽도 같은 함수를 거치며, BE 는 그 토큰 집합으로 조회한다
(`WordSceneCandidateAdapter` 의 `paradedb.term_set('tokens', …)`). 그래서 글자와 검색은
어긋난다.

| 라벨 → 관측 | 글자 | 토큰 | 검색 |
| --- | --- | --- | --- |
| `지폐를 넣고` → `지패를 넣고` | 오독 | `(지폐, 넣)` → `(지패, 넣)` | **닿는다** (`넣`) |
| `버튼을 꾹 누르면` → `버른을 록누르면` | 오독 | `(버튼, 누르)` → `(버른, 록, 누르)` | **닿는다** (`누르`) |
| `트리가 반짝반짝!` → `트리가 반적반데!` | 오독 | `(트리,)` → `(트리가, 반적반)` | 못 찾는다 |
| `꿀꺽` → `꿀꺽` | **정확** | `()` → `()` | **못 찾는다** |

마지막 줄이 이 티켓의 대표 사례다. `꿀꺽` 은 Kiwi 가 내용어로 보지 않아 색인 토큰이
**빈 튜플**이고, 질의 `꿀꺽` 도 `query_normalization` 이 "내용어가 없다" 로 거부한다.
자막바 전체 `7년간 1,387억 '꿀꺽'` 을 읽어도 토큰은 `(7, 1,387)` 이라 그 두 글자는
어디에도 남지 않는다.

**즉 이 한 건에 한해 OCR 은 병목이 아니다.** 인식을 완벽하게 고쳐도 `꿀꺽` 으로는
검색되지 않는다. 고칠 자리는 토크나이저 쪽이고 이 티켓 밖이다.

그래서 하네스는 축을 둘로 나눴다 — 글자는 `exact`/`misread`/`miss`, 검색은
`reachable`/`lost`/`unsearchable`. `unsearchable` 은 검색률 분모에서 뺀다. 이 단계를
고쳐도 움직이지 않는 수를 분모에 두면 그 비율로는 아무것도 판단할 수 없다.

### `unverified` 는 색인을 막지 않는다

같은 리뷰가 둘째로 짚었고, 이것도 맞았다. 이 절의 초판은 "표시 없는 오독" 을
**검색에 새는 오독**으로 셌다. 계약이 반대로 정하고 있다.

> **`unverified` 는 담을 컬럼이 없다.** … 이 필드는 저장 대상이 아니라 BE 가
> `tag_evidence.verification_status` 를 정할 때 쓰는 값이고 …
> **미달 관측도 전부 온다.** … **BE 는 `unverified: true` 인 행을 거절하면 안 된다.**
>
> — [`docs/contracts/job-api.md`](../../docs/contracts/job-api.md) §4.3.2

BE 구현도 그대로다. `JdbcWorkerStageOutputAdapter` 는 모든 관측의 토큰을 저장하고,
검색 질의에는 confidence 나 검증 상태 조건이 없다. **오독은 표시가 붙든 말든 색인에
들어간다.**

그래서 "표시 없는 오독" 은 **confidence 분포를 보는 값**으로만 남기고
(`unflaggedMisread`), 색인이 실제로 오염되는 양은 따로 센다 — `strayTokens`, 화면에
근거가 없는데 색인에 들어가는 토큰의 수다. 짝이 맞은 관측이든 오탐이든 가리지 않는다.

오독의 모양은 세 갈래였다.

| 갈래 | 예 |
| --- | --- |
| 앞뒤 글자를 잃는다 | `올림픽 G-1년 페스티벌` → `-림픽 G-1년페스티벨`, `경기 종목` → `경기종`, `ACELITES` → `CELITES` |
| 닮은 글자로 바뀐다 | `페스티벌` → `페스티벨`, `Best Product pavilion` → `Best Probuct pavliet` |
| 이웃 문구가 붙는다 | `컬링` → `컬링curing`, `Biathlon` → `Bicthion 바이애슬론` |

QA 가 보고한 `꿀꺽` → `꿀찍` 은 둘째 갈래다.

### 움직인 축은 하나였다 — 검출 입력 크기

`det_unclip_ratio`·`det_thresh`·`det_box_thresh` 는 단독으로는 아무것도 바꾸지 못했다.
바꾼 것은 `det_limit_type`·`det_limit_side_len` 이다.

**§8 이 적어 둔 사실이 여기서 비용으로 드러난다.** 기본값 `max`/960 은 이 표본
(800x450)에서 **아무 일도 하지 않는다** — 긴 변이 이미 960 미만이라 축소가 일어나지
않는다. 즉 검출기는 지금까지 800x450 을 그대로 보고 있었다. `min`/1280 으로 바꾸면
짧은 변을 1280 에 맞춰 **키워서** 넣는다(2276x1280). 검출기가 더 많은 픽셀을 보니
상자를 더 찾고 글자를 더 제대로 감싼다.

**인식이 읽는 픽셀은 여전히 원본이다.** §8 이 적은 그대로다 — 상자는 원본 좌표로
돌아오고 인식은 원본 이미지에서 잘라낸 조각을 읽는다. 달라지는 것은 "어디를 자르느냐"
이고, 오독의 첫째 갈래(앞뒤 글자를 잃는다)가 줄어드는 이유가 그것이다. `upscale-2x`
행이 그 구분을 보여 준다 — 그쪽은 이미지 자체를 키워 인식 픽셀까지 바꾸는데,
검출 입력만 키운 `det-min-1280` 보다 성적이 낮다.

`box-0.8` 대조군이 그 해석을 뒷받침한다. 상자 점수만 올리면 정확일치가 11/37 로
무너진다. 같은 값이 `min`/1280 과 함께면 **최고 성적**이 된다 — 큰 입력이 만들어 낸
후보가 많아야 그 문턱이 거르는 역할을 한다.

### 그래도 정본을 바꾸지 않았다

후보는 `det_limit_type = "min"` · `det_limit_side_len = 1280` · `det_box_thresh = 0.8`
이고, 이 표본에서 정확일치 16→24, 검색 도달 21→29 다. **그런데도 `ocr.v1.toml` 은
그대로 둔다.** 세 가지 이유다.

> **오염 토큰은 줄지 않는다 — 33 그대로다.** 검출 입력을 키우면 읽어 내는 문구가
> 늘지만 근거 없는 토큰도 같이 늘어서, 둘이 상쇄된다. `det_box_thresh` 없이 입력만
> 키운 `det-min-1280` 은 도달 30/37 로 가장 높으면서 오염이 **81** 까지 뛴다. 상자
> 점수가 하는 일이 그 상쇄다.
>
> 오염만 놓고 보면 더 나은 줄이 있다 — `det-min-1152-box-0.8` 은 도달 28/37 로 한 건
> 적은 대신 오염 **28**, 오탐 **0** 이다. 전환을 실제로 검토할 때는 이 줄도 후보에
> 넣어야 한다. 지금 하나를 고르지 않는 이유는 아래 셋 중 셋째와 같다.

1. **시간이 2.3배다.** 469 → 1,099 ms/장(아무것도 돌지 않는 장비에서 연달아 측정).
   76초 클립에서 이 단계가 10초에서 23초가 된다. §9 가 이미
   "세 단계 합이 30초 안팎이라 §8.2 의 30초 목표에 빠듯하다" 로 적었고, 남은 일곱
   단계가 아직 붙지 않았다.
2. **이 설정의 효과가 해상도에 달려 있다.** `min`/1280 이 800x450 에서 하는 일은
   2.8배 확대다. 1080p 입력에서는 1.2배뿐이라 **같은 이득이 날 이유가 없다.** 이 표는
   "1280 이 좋다" 가 아니라 "검출기가 800x450 보다 많은 픽셀을 봐야 한다" 를 말한다.
3. **표본이 클립 한 편이다.** FRD §11 이 요구하는 실측은 했지만 일반화 근거는 아니다.

그래서 이 절은 **후보와 그 근거를 기록하는 데까지**다. 전환 조건은 §11 에 적는다.

### 인식 모델로는 고칠 길이 지금 없다

둘째 갈래(닮은 글자로 바뀜)는 인식 모델의 문제다. 그런데 rapidocr 3.9.2 의 모델
목록에 **`korean_PP-OCRv5_rec_server` 가 없다.** 한국어 인식은 `mobile` 판 하나뿐이고
server 판이 있는 것은 `ch` 와 `en` 이다. `det_model_type = "server"` 로 바꿀 수 있는
것은 검출기뿐이다(§2 의 표가 검출 server 를 잰 것도 그래서다).

세대를 내린 `PP-OCRv4` 는 더 나빴다. 남은 길은 셋이고 전부 이 티켓 밖이다 — 한국어
server 인식 모델이 **어느 배포판엔가 있는지부터 확인하기**(rapidocr 목록에는 없다),
한국어 인식 모델 파인튜닝, VLM 에게 읽히기(§2 가 뺀 이유가 그대로 유효하다).

### 남은 실패가 무엇인지

후보 설정에서도 남는 13건 중 **영문 표기가 6건**이다(`Curling`, `Best Product
pavilion` 2건, `Beauty Style`, `GANGWON PROVINCE` 2건). 한국어 인식 모델이 로마자에
약하다.
§11 의 "뉴스 하단 자막바를 아직 못 봤다" 와 별개로, **간판·현판의 영문 병기**가 이
표본에서 드러난 약점이다.

### 표본 밖에서 확인했다 — 후보 설정은 일반화되지 않는다

시연용 클립 15편(`samples/sample_0921`, 654초, 7개 분류)을 실제 report 경로로 돌렸다.
**`꿀꺽` 이 나오는 화면은 그 안에 없었다**(원본은 2023-09-08 방송분이고 이 15편에
없다). 대신 같은 유형이 그대로 재현됐고, 그중
하나가 특히 선명하다 — 15번 클립(`KNE_10065`, 문화뉴스)의 눈사람 모형에 달린 간판이다.

화면은 `지폐를 넣고 / 버튼을 꾹 누르면 / 트리가 반짝반짝!` 이다.

| 프레임 | 기본 설정이 읽은 것 | confidence |
| --- | --- | --- |
| `s0023/kf-000072733` | `지패를 넣고` · `버른을록누르면` · `트리가 반력반력!` | 0.88 · 0.82 · 0.74 |
| `s0023/kf-000073267` | `지패를 넣고` · `버른을 록누르면` · `트리가 반적반데!` | 0.82 · 0.74 · 0.80 |
| `s0023/kf-000073767` | `지패를 넣고` · `트리가 변력번력!` | 0.81 · 0.77 |
| `s0023/kf-000074967` | `지매를 넣고` · `버른을록누르면` · `트리가 반적반픽!` | 0.84 · 0.88 · 0.77 |

**같은 문구가 프레임마다 다르게 틀린다.** 열한 건 전부 `min_confidence`(0.70)를 넘겨
`unverified` 표시가 붙지 않지만, 표시는 색인을 막지 않으므로(위) 그것과 무관하게
**열한 개의 틀린 문구가 전부 색인에 들어간다.**

**`지폐` 로 검색하면 0 건이다.** 관측 `지패를 넣고` 의 토큰은 `(지패, 넣)` 이고 질의
`지폐` 의 토큰 `(지폐,)` 와 겹치지 않는다. 문구 전체(`지폐를 넣고`)로 물으면 `넣` 이
겹쳐 닿지만, 사람이 실제로 치는 것은 낱말 쪽이다. **`reach` 는 문구 전체를 묻는
경우를 재므로 이 실패를 낙관적으로 센다** — 아래 한계에 적었다.

그래서 이 세 문구를 `eval/ocr/cases.json` 에 등록하고 스윕 전체를 다시 걸었다.

```bash
uv run --directory ai python eval/ocr/ocr_bench.py --cases-only --variant all
```

| 사례 | 보고된 오독 그대로 | 다르게 오독 | 문구가 사라짐 | `fixed` |
| --- | --- | --- | --- | --- |
| `트리가 반짝반짝!` | 4 | 13 | 3 | **0** |
| `지폐를 넣고` | 9 | 5 | 6 | **0** |
| `버튼을 꾹 누르면` | 6 | 4 | 10 | **0** |

**`fixed` 가 한 칸도 없다.** 위 표에서 정확일치를 16→24, 검색 도달을 21→29 로 올린 후보 설정
(`min`/1280 + `box` 0.8)도 여기서는 세 문구를 **전부 놓친다** — `det_box_thresh` 0.8 이
이 간판의 흐린 상자를 걸러 버린다.

이것이 "표본이 클립 한 편이다" 가 실제로 무엇을 뜻하는지다. **라벨된 클립에서 가장
좋았던 설정이 표본 밖 클립에서는 더 나쁘다.** 정본을 바꾸지 않은 판단의 근거가 하나
더 생겼고, 1080p 재측정 전에 확정하지 않는다는 §11 의 게이트가 그대로 유효하다.

### 어디가 약한지는 좁혀졌다

같은 15편에서 **뉴스 하단 자막바(슈퍼)는 잘 읽힌다.** §11 이 "아직 못 봤다" 로 남겨
둔 항목인데, 이 자료에 들어 있었다.

```
'이것은 군사 정찰위성이 실제 정찰 능력보다는 김정은의'
'국방 치적을 과시하는 목적이라는 것의 방증이기도 합니다.'
"'누리과정 예산 미편성은 교육감 직무 유기'"
'최경환 경제부총리'
```

앞의 두 줄은 그 클립의 자막 파일과 **글자 단위로 일치했다**(NFKC·공백 제거 기준).
나머지는 화면에만 있는 문구(이름표·출처 표기)라 자막과 대조할 수 없다.

그래서 이 단계의 약점은 "한국어를 못 읽는다" 가 아니라 **짧고 대조할 이웃이 없는
글자**로 좁혀진다. 이 표본에서 그것이 나온 곳은 현장 소품·간판·전시물의 작고
저대비이며 기울어진 글자였다.

**그러나 자막바가 안전하다는 뜻은 아니다.** 뒤늦게 들어온 화면 증거에서 원 사례가
바로 자막바였다(아래). 자막바의 **긴 문장**은 지금도 쓸 만하다 — 사건명·인물·수치가
거기 있고 위 두 줄은 글자 단위로 맞았다. 틀리는 쪽은 어느 경우든 **표시 없이
색인된다.**

### 원 사례의 화면 증거 — 자막바였고, 장면 설명까지 번졌다

원본 클립은 끝내 확보하지 못했지만, **결과 화면 캡처가 뒤늦게 들어왔다.** 경남은행
횡령 보도의 자료 화면이고 방송일은 2023-09-08 이다 — 시연용 15편에 없는 클립이다.

**캡처 자체는 커밋하지 않는다.** 방송 화면이고, `.gitignore` 가 `samples/*` 를 막아
둔 이유(FRD §6.4 · S15P21A501-134 의 dataset 권리 Gate S)가 정지 화면에도 그대로
적용된다. 커밋되는 것은 그 화면을 보고 적은 **글자 라벨**이다 —
`samples/ocr-ground-truth.*.json` 과 같은 취급이고, 그 라벨이
[`eval/ocr/cases.json`](../eval/ocr/cases.json) 의 `expected` 다. 캡처는 제보자 쪽과
작업자 로컬에 있다.

화면 아래 자막바는 `7년간 1,387억 '꿀꺽'` 이다. 파이프라인은 `'꿀찍'` 으로 냈다.

이 한 장이 위에서 내린 결론 두 개를 고친다.

**하나. 현장 간판이 아니라 자막바다.** 이 문서는 표본 안에서만 보고 약점을
"현장 소품·간판" 으로 좁혀 놓았고, 자막바는 "쓸 만하다" 로 남겨 두었다. 원 사례는
그 반대편에 있다. 다만 틀린 자리는 자막바의 **긴 문장이 아니라 따옴표 친 두 글자**다.
15편에서 글자 단위로 맞았던 것은 전부 한 줄짜리 인용문이었다. 그래서 축은
"자막바냐 간판이냐" 가 아니라 **대조할 이웃 글자가 있느냐**로 다시 그어진다 — 두 글자
강조어에는 문맥이 걸릴 데가 없다.

**둘. 영향 범위가 색인 토큰에서 끝나지 않는다.** 티켓의 제약은 "검색 근거로 OCR
토큰이 쓰인다" 지만, 캡처에서 `꿀찍` 이 찍힌 자리는 **검색 근거로 표시된 AI 장면
설명**이다. 코드가 그 경로를 그대로 갖고 있다.

| 자리 | 하는 일 |
| --- | --- |
| [`vlm_metadata/grounding.py`](../src/npick_worker/vlm_metadata/grounding.py) | OCR 관측을 `{"ocr": [{"label", "rawText", …}], "transcript": […]}` 로 직렬화한다. `rawText` 는 **원문 그대로**이고 교정 단계가 없다 |
| [`vlm_metadata/prompt.py`](../src/npick_worker/vlm_metadata/prompt.py) | 그 JSON 을 user prompt 의 `{grounding}` 에 채운다 |
| [`config/vlm_metadata.v2.toml`](../src/npick_worker/config/vlm_metadata.v2.toml) | 정본 설정이고 `{grounding}` 을 갖고 있다 — 즉 이 경로는 **켜져 있다** |

그래서 오독 하나가 세 곳에 동시에 들어간다 — (1) `ocr_observation.tokens` 색인,
(2) 사용자에게 보이는 장면 설명 문장, (3) 그 설명으로 성립하는 "장면 설명 일치" 근거.
`unverified` 표시는 (1) 에만 붙을 수 있고 (2)·(3) 으로는 따라가지 않는다.

**가리지 못한 것.** 원본 프레임이 없으므로 **이 `꿀찍` 이 OCR 출력 그대로인지, VLM 이
키프레임을 보고 따로 쓴 것인지는 확정할 수 없다.** 확인된 것은 경로가 열려 있다는
사실까지다. 클립을 받으면 그 장면의 `ocr.json` 한 줄로 갈린다.

**등록부에는 여전히 `frame-missing` 이다.** 캡처는 UI 화면이지 keyframe 이 아니라서
엔진에 넣을 수 없다. 회귀로 잡히는 것은 아래 세 사례뿐이다.

### 그래서 이 티켓이 남기는 것

1. **고치지 못했다.** 설정으로 닿는 범위에서는 이 오독을 없앨 수 없다. 완료 조건의
   "사례 개선 또는 한계 문서화" 중 뒤엣것이다.
2. **재현과 회귀는 생겼다.** `eval/ocr/` 이 정확일치를 재고 `cases.json` 이 사례를
   붙잡는다. 인식 모델을 바꾸는 후속 작업은 이 세 사례가 `fixed` 로 바뀌는지로 판정한다.
3. **검색 관점의 지표가 생겼다.** 초판은 정확일치를 검색률로, "표시 없는 오독" 을
   색인 누출로 읽었고 **둘 다 틀렸다**(위 두 절). 지금은 토큰으로 재고
   (`reachable`/`lost`/`unsearchable`), 색인 오염은 `strayTokens` 로 따로 센다.
4. **`꿀꺽` 원본 클립은 아직 없다.** 화면 증거는 생겼지만 UI 캡처라 엔진에 넣지
   못한다. 등록부에 `frame-missing` 으로 남아 있고, 클립과 시점을 받으면 `frame`
   한 줄로 회귀 검사에 들어온다.
5. **OCR 오독은 장면 설명으로 번진다.** 위에서 확인한 경로다. 이 단계의 품질을
   "검색 토큰의 품질" 로만 보면 영향 범위를 과소평가한다.
